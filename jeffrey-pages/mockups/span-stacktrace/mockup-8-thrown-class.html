The thrown exception, in the stack

Folding the constructor chain away was right — but it took java.io.IOException.<init> with it, and that was the one place the thrown class appeared inside the stack. So the question is where it belongs now: in the panel chrome, as line one of the stack the way a JVM prints it, or both. Every variant below shows the same caught IOException and, underneath, exactly what its Copy button would put on your clipboard — which is where the difference stops being cosmetic.

The class and message live in the panel chrome and the stack is frames only. That reads fine on screen — but folding the constructor chain took the class out of the stack itself, and Copy was already emitting frames with no header line. What it puts on the clipboard is not a stack trace: no tool will parse it, and pasted into an issue it says what happened nowhere.

If you want one answer

3. The redundancy is the point rather than an oversight: the chrome line is the label on a throw the reader has not opened yet, and the JVM line is part of the stack trace itself — the thing you select, copy and paste. Take either one away and something breaks: without the chrome, a span with three collapsed throws is three rows saying only caught; without the line, Copy keeps producing something no tool will read.

Pinning it (from 2) costs nothing and pays on exactly the stacks where it matters — a 253-frame stack scrolled forty rows down still says what was thrown.

Whichever wins, Copy gets the header line. That half is a bug fix, not a preference — the function's own comment claims it emits "the shape a JVM prints it".
