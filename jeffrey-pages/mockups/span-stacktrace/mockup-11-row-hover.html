Throw row hover

The first row in each panel is drawn hovered, at the width a real trace modal gives this region — which is the width that makes today’s version look like a slab. Everything else is identical.

0 Todaythe problem

The first row is hovered. Two things are wrong and neither is the idea. The tint is --color-primary-light — a saturated lavender — where the app hovers rows with --color-bg-hover, a near-white #f9fafd, in both TraceCardList and TraceOperationSummary. And the row is the full width of the panel while its content occupies the first fifth. Measured at this width: the highlight is 1886px wide and the ink ends at 238px, so 87% of it is empty — a saturated fill at that ratio is a slab with a little text stranded at the left. Blue in a red region does not help either.

1 The app's row hoverrecommended

Exactly what .trace-row and .span-grid-row already do: --color-bg-hover. Near-white, so width stops mattering — a slab of #f9fafd reads as a lit row rather than a block of colour. The caret takes the primary tint, which is where the affordance belongs anyway.

2 The waterfall's hairlines

The convention of the component this panel lives inside: .wf-row:hover draws no fill at all, just an inset hairline top and bottom in primary. Immune to width by construction, and a reader who has been hovering span rows all along has already learned it. Two lines across a wide panel can read as a divider rather than a highlight.

3 Edge and fill

The app’s fill plus a 2px primary bar at the left edge, where the caret and the row both start. Anchors the highlight to the end you are reading from rather than letting it float across the width. Costs a second signal for one state.

4 Only the control reacts

Nothing happens to the row: the chevron takes colour and a soft disc, and the class name tints. Width becomes irrelevant because nothing is filled. The quietest option by a distance — and the one most likely to be missed, since the pointer is rarely over the caret when it enters the row.

5 Fill only the content

Attacks the complaint literally: the tint stops after the content instead of running the panel width. Fixes the slab while keeping a visible fill. But the stopping point is a guess — a long class name or message runs past it — so it trades a slab for a ragged edge that moves with the data.

If you want one answer

1. The row was not wrong to highlight; it was wrong about which highlight. The app already has a row-hover token and two other components already use it. At #f9fafd the width stops being a problem on its own, without inventing a shape.

2 is the better argument if you weigh consistency with the immediate surroundings over consistency with the app: these rows sit inside the waterfall, and the waterfall hovers its own rows with hairlines and no fill. Picking it makes the span detail agree with the thing it is nested in rather than with lists elsewhere.

5 is the trap. It fixes exactly the thing that looks wrong, and introduces an edge whose position depends on how long the class name happens to be.
