How big the source column should be

The same stack in every panel — the Reader$2.ensureOpen throw up through the OGNL parser into MyBatis, from the screenshot that prompted this — drawn at the docked strip’s real width. Only the right-hand column’s treatment differs. The chips beside each heading are measured by the page itself when it loads: the size the browser resolved, the widest source cell, and how many signatures that width actually truncates.

0 Todaythe problem

.st-src is --font-size-xs — 0.6rem, 9.6px — against a signature at 0.7rem beside it, and on a library frame it is coloured --color-text-light (#b6c1d2), the palest text token the app has. Two problems, not one: 9.6px is under the ~10px floor most UI text respects, and it is drawn in the faintest ink available. On the OGNL run above that is a whole screen of pale grey numerals.

↔ Where the width actually costs something

Every panel above says 0 signatures truncated, which is worth checking rather than trusting: .st-fr is grid-template-columns: 1fr auto, so a wider source column takes its width straight out of the signature, and the signature is text-overflow: ellipsis. So here is today against the pick at 620px — narrower than this panel has ever actually been drawn, and narrow enough that both of them clip. They clip the same three signatures. The 25px the bigger source column takes costs no frame its name, even here, so the width objection to raising it does not survive being measured.

The pick, and the thing worth noticing

2 — 0.68rem with --color-text-muted. It moves both halves of the problem, it keeps the source a step under the signature so the columns still read as different things, and it is not invented: it is what the thread-dump frame list in ProfileHeapDumpThreads has been drawing this same content at all along. Two stack views in the app that disagree about how to render a frame is a bug in its own right.

Size was only half of it. The chips above each panel measure the resolved font size, and the jump from 9.6px to 10.9px is real but small — what actually makes the numbers readable in panel 2 is dropping --color-text-light (#b6c1d2) for --color-text-muted (#748194). Any variant that raises the size and leaves the colour alone (variant 1) fixes less than it looks like it does.

The width objection does not survive measurement. A wider source column does take its width out of the signature, but the section above forces both into a 620px panel and they clip the same three signatures — the extra 25px costs no frame its name. So this is a choice about legibility alone. Take 4 instead if the fold bars being left behind at 9.6px bothers you more than the extra height costs.
