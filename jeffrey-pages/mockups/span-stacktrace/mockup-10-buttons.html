Stack toolbar buttons

All five draw Option 1 — the stack pill gone, a chevron in the gutter, the whole row toggling, the foot carrying only the verdict. The only difference is the toolbar in the stack header. The size beside each heading is measured from the rendered button, not typed in, so “bigger” is a number. The application has no shared Button component — it uses Bootstrap classes restyled with tokens in assets/styles.scss, and those rules are copied verbatim into this page.

3 Full size

No -sm: .5rem 1rem and 0.875rem text, the size the app uses for page-level actions, included so the ceiling is visible rather than guessed at. It does not break the layout: measured down to 680px the toolbar never wraps and never collides with the frame count. So the objection is dominance rather than fit — at three and a half times the chip’s area, the header stops serving the stack beneath it and starts competing with it.

If you want one answer

1. It is the application’s own idiom applied without inventing anything: the same btn btn-sm with the same btn-primary / btn-outline-secondary swap that three other profile views already use for a toggle. Roughly double the area, square corners like every other button, and nothing new for a reader to learn.

4 is the one worth arguing for if you want the panel to be right rather than merely consistent. Fold libraries genuinely is a state, and the reader met that exact switch in the waterfall toolbar minutes earlier. The cost is two control shapes in one row. 5 is the only variant that names the off state, which is a real advantage on a control whose off state is not obvious.

3 is included as a ceiling, not a candidate. It fits — measured down to 680px nothing wraps and nothing collides — but at three and a half times the chip’s area a header that large competes with the stack beneath it, which is the opposite of what a header should do.
