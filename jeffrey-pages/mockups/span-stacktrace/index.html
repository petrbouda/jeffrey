Exception stack traces in the Trace Modal

The trace modal already shows every throw attributed to a span — class, message, offset, and whether it escaped. What it cannot show is where it was thrown, so a reader who gets that far still has to leave the trace to find out. The data is already there: stacktraceId is on TraceExceptionRow and already reaches the browser, and nothing consumes it yet. What is missing is one repository read, one endpoint, and a decision about the screen — which is what these five were for. Every page draws the same span, the same three throws, and the same 45-frame stack, so the only variable is layout. The answer is a combination of two of them — the final design is first below, with the five it came from underneath it.

Final — folded stack, previewed on the rail chosen

Directions 3 and 5, which were never rivals: one is where a stack is glimpsed, the other is how a stack is drawn. Each one’s weakness is the other’s strength. A four-line popover preview is wasted when three of those lines are java.util.stream — folding fixes that. An inline stack was ruled out because 45 frames wreck the panel — folding fixes that too, at 9 rows. So neither of the extra windows the other three needed has to be built, and the trace never leaves the screen. Carries the fold rule stated once, and the library-only floor that keeps it from folding a stack down to nothing.

Already in place, so none of the five has to build it

  • The reference. trace_exceptions.stacktrace_hash is derived and stored; its javadoc calls it “what decides whether the drill-down offers a stack at all”.
  • The frames. stacktraces.frame_hashes joined to frames, with the unnest(...) JOIN frames idiom already used in JdbcProfileToolsRepository.
  • The order. The parser stores getFrames().reversed(), so the array is root-first and the last element is the throwing frame. A top-down stack reads it backwards.
  • The IDE. IdeClient.fetchSource(), IdeButtonGate.hasClass() and SourceViewerModal already exist and are profile-scoped — frames here can open real source, which no other stack display in the product does.

The five it came from

1

Disclosure in place cheapest

A caret on the throw row unfolds the frames underneath, in the region the reader is already looking at. Nothing new opens. The cost is height: 45 frames push everything below off screen, and truncating just moves the question to “how many is enough”.
2

List left, stack right

Two columns: the throws stay a compact list, the selected one’s stack fills a pane that scrolls on its own. The region’s height stops depending on stack depth. Costs horizontal room the panel does not have, and earns nothing on a span with a single throw.
3

The stack reaches the timeline in the final

The rail’s existing cross popover gains the top four frames, so the answer arrives on hover with no click and no span opened. A preview is all it can be — the popover is capped at 13rem — so this is a front door for one of the others, not a rival to them.
4

A window of its own most capable

The wide near-fullscreen pattern over the trace modal. Room for the whole stack plus the things a cramped panel cannot host: copy-as-text, an app-frames filter, and per-frame open-in-IntelliJ. Costs a modal on a modal — and the timing context behind it is what you lose while reading.
5

The stack, minus the noise in the final

Attacks the problem rather than its placement: 45 frames of which eight are the reader’s own code, so runs of library frames collapse into one expandable bar each. 9 rows instead of 45, nothing lost, one click to see any of it. Includes a side-by-side of both stacks.

Since it shipped

The docked strip: smaller, and told apart

The strip and the card under it are the same white. Five ways to separate them, all at one size reduction, drawn inside the real card — and each measuring its own contrast against the ground it sits on.

The offset leaves the dock header for good and Select … comes down beside Fold libraries — same btn btn-sm box, five colour treatments, plus the two readings of "left of".

The critical-path line comes out of the timing block, and the recording offset moves from the far right of the foot up beside the duration it is an offset of. Drawn on the component's own CSS, with a note on what the removal costs.

How big the source column should be

The right-hand Reader.java:175 column renders at 9.6px in the app's palest text token. Five treatments on the OGNL stack that prompted it, each measuring its own resolved size and how many signatures it clips.

Expand button, under the time offset

The row stays clickable and gains one button, stacked in the gutter below the offset — space the layout was already throwing away, so it is free on any throw that carries a message. Five skins for it, including one whose label is the frame count.

Throw row hover

The hover fills 1886px for 238px of ink — 87% empty — in a lavender the app does not use for rows. Five treatments, each with a ledger of which padding and margin it deletes: the head’s negative-margin pair exists only to be filled, so a treatment that does not fill it does not need it.

Stack toolbar buttons

Option 1’s rows with five treatments of Fold libraries and Copy. The chips are off-system three ways, not just small — smaller than the app’s smallest button and pill-shaped where every other is square. Sizes are measured from the rendered box.

Opening a throw’s stack

Dropping the stack pill — a third control in a row that already carries a class, a message and a verdict, with a target a few pixels wide. Five replacements, from “the row is the control” to no control at all.

The thrown exception, in the stack

Folding the constructor chain took IOException.<init> with it — the one place the thrown class appeared inside the stack. Where does it go now? Each variant shows what its Copy button would put on the clipboard, which is where the difference stops being cosmetic.

The popover, at five sizes

Drawn against a real 253-frame stack from a MyBatis/OGNL throw. Size is only one of the three things wrong with the shipped popover — the worst is that the row truncates from the right, so the package survives and the class and method, the half worth reading, do not.

How they relate, before you pick

  • 1, 2 and 4 were the alternatives — they answer the same question, “where does the stack live”, and only one could win. The final answers it with 1’s placement, which only became viable once 5 made the stack short enough to sit there.
  • 3 and 5 were never in that contest, which is why they combine instead. The popover is a place, the fold is a rendering; putting the second inside the first costs nothing and makes both better.
  • What the final gives up is direction 4’s room — there is still nowhere good for copy-as-text, and no per-frame IDE link surface beyond the hover affordance. That is the trade, stated on the final page rather than buried here.

Static mockups — no production code changes. The span notifications set next door settled the rails and the detail regions these build on. With the direction settled, the backend is one repository read and one endpoint on TracesController: resolve a stacktraceId to its frames, newest frame first. The fold is a frontend concern — the endpoint returns every frame.
