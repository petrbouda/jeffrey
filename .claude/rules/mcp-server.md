## MCP server and plugin rules

### One AI integration, one direction
- Jeffrey never calls a model provider. No in-app assistant, chat, OQL helper, provider setting or secret storage — every earlier one is now a plugin skill over the MCP server. A feature that would put a model *inside* Jeffrey must be a skill or a tool instead.
- The endpoint is `POST /api/mcp`, installation-wide, `profileId` as a tool argument. It is served by **Spring AI's modern (stateless `2026-07-28`) MCP server** (`spring.ai.mcp.server.protocol=MODERN`, `.modern.mcp-endpoint=/api/mcp`) — Streamable HTTP, so a `tools/call` answer is an SSE stream that carries `notifications/progress` for long work and the final `CallToolResult` on the same response. It is the only MCP endpoint and the only address: the old `/api/internal/…` alias and the loopback `claude-code` endpoint are gone — do not map a second path.
- Off only by `jeffrey.microscope.mcp.enabled` (read at startup, the guard filter 404s the endpoint when false). `connector_` and `ide_` have their own switches (`…mcp.connector.enabled`, `…mcp.ide.enabled`) because they reach outside the server. `…mcp.families` narrows what is advertised; `…mcp.preset` (`all|jfr|heap|connector`) picks a selection when that list is empty; `recordings` must stay selected wherever `connector` is (`ExternalMcpProperties`). Next-step hints to another family go through `AdvertisedFamilies.hint` (one `@Bean`), and `McpInstructions.text(AdvertisedFamilies)` describes only the advertised families.
- `McpRequestGuard` always rejects a `Host` outside `jeffrey.microscope.mcp.allowed-hosts` (loopback by default) and then a foreign `Origin` — both `403` with a reason naming the fix. `jeffrey.microscope.mcp.trust-forwarded-headers` (default false) takes host/scheme from the first `X-Forwarded-Host`/`X-Forwarded-Proto` for both checks, for a Jeffrey reachable only through a proxy. `jeffrey.microscope.mcp.token` is an optional bearer token checked last: when set, a missing or wrong `Authorization: Bearer` gets `401` + `WWW-Authenticate: Bearer` (constant-time compare, token never logged); when empty, any `Authorization` header is ignored, so manifests always send one. Refusal kinds are the sealed `McpRequestGuard.Refusal` (`Unauthorized`/`Forbidden`).

### One `mcp-server` module holds the protocol types + the `@Tool` adapter; the server itself is Spring AI's, wired in `core`
- **The MCP server is Spring AI 2.1.0's modern server** (MCP Java SDK 2.2.0), configured in `core`'s `McpConfiguration` and `application.properties`. Jeffrey does not hand-roll the protocol: the SDK validates `2026-07-28` requests, maps errors, emits the result envelope and streams. A **shallow programmatic bridge** adapts Jeffrey's tools onto it: `McpToolBridge` (spec/outcome/elicitation ↔ SDK types), `JeffreyToolRepository` (a custom `McpSyncToolRepository` over `McpToolsetAssembler`, routing `jeffrey/cost=SLOW` tools to `McpSyncResponse.streaming`), `SkillsFeature` (the `io.modelcontextprotocol/skills` extension as a custom `McpFeature`), `CompletionsFeature` (`completion/complete` as a custom `McpFeature`), the resource/prompt repositories, and `McpGuardFilter` (runs `McpRequestGuard` in front, with the SDK's `ServerHttpHeaderValidator` left NOOP so there is one authority). Do not re-add a hand-rolled dispatcher, validator or controller.
- **`jeffrey-microscope/mcp-server`** (one module and JPMS module `cafe.jeffrey.microscope.mcp.server` — the former `mcp-protocol` was folded in when the hand-rolled protocol went away) holds two things in one package. **The MCP `2026-07-28` types and SPI:** the tool/prompt/resource/completion SPI (`McpToolProvider`, `McpToolSpec`, `McpToolResult`, `McpToolOutcome` (a result or an `InputRequired` — no `Deferred`), `CompositeToolset`, …), `McpCallContext` (carrying `McpClientCapabilities` and an `McpProgressSink` for streamed progress), the skills and input-request extensions, the output-schema tooling (`McpSchemaGenerator`, `@McpOutputSchema`, `@McpNullable`, …), `McpCursor`, `McpText` (capping), `McpProtocolVersions`, and its own mapper (`McpJson`, configured as `core`'s `Json`). **And Jeffrey's `@Tool` adapter:** `ReflectiveToolset` (`@Tool`→MCP)/`ProfileScopedToolset`/`ToolMethodIndex`, `ToolInvocation` (the JFR span), the hints (`@McpToolMeta`, `McpToolCost`, `McpToolRequirement`, `@McpToolHints`, `JeffreyMetaKeys`), `McpToolNames` (family and title), `McpNextTool`/`McpFollowUp`, `finding/*`, `McpToolOutput`, `McpToolMetrics`, and `JeffreyMcpServer` (the identity, the cursor codec, `serverVersion()`/`supportedProtocolVersions()`). Its test-jar carries the generic helpers (`…server.testing`: `McpTestRequests`, `McpSchemaConformance`) and Jeffrey's own (`McpNextToolConformance`, `McpTestToolsets`).
- **The result limit** is `McpToolOutput.MAX_CHARS`: text is capped, and structured content past it is refused as the tool's error (`McpToolResult.OVERSIZED_STRUCTURED_CONTENT`) inside the call by `ToolInvocation`, so the span fails, a resource read is `-32602` and a completion is empty. A tool that fails inside Jeffrey surfaces as a `CallToolResult` with `isError` carrying the reason.
- `McpToolProvider` cannot be sealed, so `McpToolProviderImplementationsTest` (core) fails on any implementation but `ReflectiveToolset`, `ProfileScopedToolset` and `CompositeToolset`. Spring AI is used for `@Tool`/`@ToolParam` and for the modern server. The module depends on `common`, Jackson, SLF4J, Spring AI and Spring Web.
- **Streamable HTTP, stateless.** A long tool runs on the call and streams `notifications/progress` (through the `McpProgressSink` on its `McpCallContext`) over the response's SSE stream, then returns its final `CallToolResult` on the same stream. There is no `Mcp-Session-Id`, no polling, no tasks extension, no `operationId`, and no cancel RPC — losing explicit cancellation is accepted (owner decision, no backward compatibility).
- **MCP `2026-07-28` only** (owner decision 2026-09-25, no backward compatibility). The SDK enforces the version, the request `_meta` and the `MCP-Protocol-Version` header; clients that cannot speak `2026-07-28` (e.g. Gemini CLI) stay unsupported. No `initialize`, no `ping`, no JSON-RPC batching, no handshake-era versions — do not add any back.
- `server/discover` is the probe and must answer even when assembling the toolset would fail — nothing on that path may resolve the toolset (`McpCompletions.isAvailable()` reads configuration for that reason). Callers that only need "is Jeffrey up" (the plugin's `jeffrey-status.sh` hook, `validate-mcp.yml`'s readiness step) use it.
- Structured results always: `tools/list` carries `outputSchema` wherever a tool has one and `tools/call` carries `structuredContent` whenever the result has it — there is no older-client text-only path. The SDK finishes each result with its `resultType` and `_meta` serverInfo.
- CI (`.github/workflows/validate-mcp.yml`) boots the jar, checks `tools/list` against `build/mcp/tools-list.snapshot.json` (`build/scripts/mcp-snapshot.py --check`, which also asserts the result envelope; the snapshot keeps each `outputSchema`'s content without descriptions and the values of every `jeffrey/*` hint, so schema drift fails CI — regenerate it from the packaged jar with `--url … > build/mcp/tools-list.snapshot.json`, never by hand), checks that the packaged jar's `skills/list` serves all thirteen skills and that discover declares `io.modelcontextprotocol/skills` (the only guard on the nested-jar skill loading), and runs the pinned MCP conformance suite twice against one baseline, `build/mcp/conformance-expected-failures.yml`: the active suite, and `server-stateless` (required by the 2026-07-28 requirement set, not in the active suite). The baseline holds only checks that call the suite's own fixtures (`test_*`, `test://*`). The `input-required-result-*` scenarios (in the 2026-07-28 requirement set) are not run: every check that exercises the server calls a suite fixture (`test_input_required_result_*`), and the two that do not (`unsupported-methods`, `validate-input`) pass; Jeffrey's own questions are pinned by unit tests. A baseline entry is one `<scenario>:<check-id>` with its reason; regenerate it from a real run, never by guessing.
- A tool's `title` is derived from its name by `McpToolNames.titleFor` (mcp-server); do not annotate it per method. `McpToolNames.familyOf` is the one reading of a tool's family.
- Tool descriptions say what the tool does, what it returns and what it is not for — at most 1 500 characters (400 per parameter), pinned by `McpToolsetAssemblerTest.noDescriptionExceedsTheHostCutoff`. Call order does not go in a description: it lives in `McpInstructions` (per advertised family) and in the skills.

### Results are typed records (Tier 3)
- **Structured output.** Every tool that answers a record declares `@McpOutputSchema(Record.class)` and returns `McpToolResult.of(record)` (text = the record's JSON) or `McpToolResult.of(markdown, record)` where the agent reads Markdown. A host may hand the model only the structured content when there is one — Claude Code does — so a Markdown document that *is* the answer (the flamegraph, differential, movement, trace and operation exports) also travels in the record's `markdown`, built with `McpToolOutput.withDocument`, which cuts it so the serialised record fits `MAX_CHARS` and hands the record the cut; a record that only counted the document (`markdownChars`) reached that model as metadata without the tree. 113 of 114 tools declare one; `ide_source` (a class's source text) is the only text-only tool, pinned by `McpToolSurfaceTest.TEXT_ONLY`. A tool with a schema must return structured content (`ToolInvocation`).
- **The generator is closed** (`McpSchemaGenerator`, mcp-server): it emits only `type`, `properties`, `required`, `additionalProperties`, `items`, `enum`, `description`, `minimum` — no `$ref`/`$defs`. Records become closed objects with every component required; `String`, booleans, integral and floating numbers, enums (their constant names), `List`/`Set`, `Map<String,T>` and `McpJsonObject` are the only other types. It refuses, with the path, `Object`, `JsonNode`, `Map<String,Object>`, `Instant`, `Duration`, `Optional`, arrays, raw/wildcard/generic types, recursive records, enums with bodies, a `toString()` or Jackson annotations, extra `get*`/`is*` methods and Jackson annotations on components — anything that would make Jackson write something the schema does not say. `@McpDescription` and `@McpMinimum` add the two optional keywords.
- **`McpJsonObject`** (`{"type":"object"}`) is the one open shape, sanctioned by component in `SpringAiToolConformanceTest.SANCTIONED_COMPONENTS`: `McpNextTool.arguments`, an operation's `result`, `McpFinding.evidence`. Type everything else; a new use needs a new sanctioned entry with its reason.
- **Null is explicit.** A component that can be absent is `@McpNullable` (schema `["t","null"]`, a nullable enum lists `null`) and is written as `null`, never omitted. Mark it only if the builder can leave it null; a component that is never null is pinned non-null by a test. `@McpNullableElement` marks nullable list/map elements (SQL NULL cells) and is refused on a bare component. A count the tool cannot know is null, never a false zero (`Figures` turns `-1`/blank sentinels into null).
- **Enums are UPPER_SNAKE constant names** on the wire, in outputs and in inputs alike, so a value round-trips; `ToolMethodIndex` binds `@ToolParamValues` inputs case-insensitively and rewrites them to the canonical spelling. `McpToolSurfaceTest` pins both directions. The one exception is `profiles_viewLink.view`, which takes Microscope route paths (echoed back verbatim, so they already round-trip) — pinned by `McpToolSurfaceTest.ROUTE_VALUED_INPUTS`; do not "fix" it to UPPER.

### Result conventions
- **Time:** every instant and window bound is UTC epoch milliseconds named `…EpochMs`, in inputs and outputs; durations carry a unit suffix (`…Ms`, `…Nanos`, never `…Millis`, no ISO strings). Windows are converted and checked only in `RecordingSpan`/`EpochWindow` (a refusal names the recording's own span). A comparison window is on the primary's clock, applied at the same offset into the baseline, and both landed windows are reported.
- **Ids:** a heap `objectId` is an unsigned decimal `String` in and out (`HeapObjectIds` parses at the boundary, 64-bit HPROF ids exceed JSON's 2^53). A well-formed but unknown id (object, operation, span, trace, event type, project) is a correctable tool error naming it; a status is only for a valid question that has no data.
- **Paging:** a result that can continue takes `cursor` and returns `hasMore` + `nextCursor` — one opaque `McpCursor` (versioned, fingerprinted to the filters; Jeffrey's codec is `JeffreyMcpServer.CURSOR`) through `OffsetPaging` or a keyset. No `offset` input, no prose paging line. A pure top-N keeps `limit` and declares its cut in the record. A paged total the tool cannot know until the last page is null while `hasMore` (`heap_oql`'s `totalCount`), never the page's size. A layer below pages once, at its boundary, and fetches one row past the page so `hasMore` is real: `heap_oql` passes the cursor's start down as a `PageWindow`. A query the Java executor walks unsorted resumes: `JavaExecutor.page` starts at the `OQLResumePoint` the last page handed back (class, instance, rows passed over) and reads nothing before it, so a deep page costs what the first does; the cursor is then a keyset of that point and the rows shown so far (a page cut for its size resumes from its own start, passing over the rows shown). Every other plan pages by offset: `OqlExecutor` cuts the page from its first `offset + limit` rows (`SqlExecutor` fetches `LIMIT n + 1`), so no executor knows offsets (`OqlPagingIntegrationTest`).
- **`followUp`** (`McpFollowUp`: `nextTools` + `guidance`), built with `NextSteps.builder(advertised)`, replaces every prose next step. `nextTools` are `McpNextTool {tool, arguments, why, weight}` with this answer's real ids, epoch-ms windows and cursors, started only with `NextCalls.to(tool)` (core), which takes `weight` from `McpToolCatalogue` — never stated at a call site; `guidance` is advice that is not a call. Calls are family-gated (a withheld family is dropped), name only event types the profile recorded (`FollowUpCalls.recordedOnCpuEvent`/`recordedAllocationEvent`, else guidance), use `nextWhen(boolean, Supplier)` so nothing is built for a branch not taken, never offer a call for what the answer already carries (a leak suspect with a `gcRootPath` gets no `heap_getPathToGCRoot`: each suspect carries its path, accumulation point and contents so one answer makes the leak claim checkable), and never offer to rebuild a success: a SLOW or recomputing call (retry, `compute`, `retry:true`) is a `nextTools` entry only after FAILED, CANCELLED, NOT_RUN_YET or NOT_COMPUTED — otherwise guidance. `McpFinding.nextTool` is an `McpNextTool`, gated with `McpFindings.reachable`. Tests check every emitted call with `McpNextToolConformance.assertFollowable`.
- **Markdown answers keep a footer.** Another host may pass only the text to the model, so a tool whose text is Markdown or fixed-width text ends it with `LinkedOutput.footed(...)`: `Open in Microscope: <uiLink>` (+ its note) and a `Next:` line per call. The body is capped first (`McpToolOutput.cappedWithin`), so the footer always survives; `MarkdownFooters.assertRenderedFrom` checks it.
- **Statuses, not text:** "no data / not recorded / not computed / not run yet" is the same record with a `status` enum and a nullable `reason` (e.g. `CatalogueStatus`, `DashboardStatus`, `AutoAnalysisStatus`), with empty collections or null data — never a text-only return, and never an empty answer that reads as a measurement: `flamegraph_export` of an event type the profile did not record answers `GraphStatus.NOT_RECORDED` naming the recorded types, with the export of the one answering the same question as its next call, rather than an empty tree.
- **Two limits, by declaration.** A tool that declares `maxResultSizeChars` (the long documents) may answer up to `McpToolOutput.MAX_CHARS`; every other tool is held to `McpToolOutput.UNDECLARED_MAX_CHARS` (50,000): a client applies its own default limit to it — Claude Code's 25,000 tokens, past which the answer is saved where the agent may not read it (measured: 42k inline, 75k and 120k saved). `FittingPage.fits`, the per-tool page checks and `EvidenceOutput`'s default budget use the undeclared limit; `jvm_threadDump` and `jfr_executeQuery` the declared one. `test-plugin-eval-mocks.py` holds every recorded answer of an undeclared tool under it. A long list is cut to what advice needs and counts the rest (`jvm_flags` lists the flags set and counts the defaults, `name` finds any; `compare_quality` lists only differing settings), never left for the cap to cut arbitrarily; a long string in a row is cut where it says least and its full length kept beside it (`jvm_system`'s command lines: `CommandLines` keeps the start and the end, `commandLineChars`).
- **Declared cuts:** a bounded list keeps the rows that matter (`latest` for time series and dumps, `worst` for rankings, `GcDetailPages.Rows`), says which in `@McpDescription`, and reports an `omitted…` count (null when unknowable); several bounded tables share one budget through `FittingPage`. A cap that belongs to a lower layer is referenced from it (engine constants made public), never copied; a list cut by a cap it did not choose has a null omitted count.
- **Tests:** `StructuredAnswers` validates `structuredContent` against the generated schema (`McpSchemaConformance`) on the data path and every status path, checks each `nextTools` entry and resolves the `uiLink`.

### UI links: data for the agent, a link for the user
- Every answer whose subject has a Microscope page carries a `String uiLink` (absolute URL, no wrapper record) built with `UiLinks.view(profileId, MicroscopeView[, query])` or `UiLinks.page(MicroscopePage)` — never a hand-typed URL — including on status answers where the page exists. A row that names something with its own page carries its own `uiLink` too — every trace (`TraceAnswers.Trace`, in `traces_slowestTraces` and `traces_attributeSearch`), operation (`TraceAnswers.Operation`) and notification exemplar (`ExemplarTrace`) — built by `TraceLinks`; the skills put each link beside the name it opens. A `uiLinkNote` says only what the link still cannot reproduce — today: `traces_spanFlamegraphExport` and `traces_operationFlamegraphExport` (the graphs open in a modal / the operation's own panels), `traces_notifications` (no notifications page; it opens the operations), `compare_movements` (the page draws the graph, not the ranking), a differential whose baseline was read past the primary's window (`compare_flamegraph`, `compare_movements`), `heap_oql` (the console opens without the query), and the heap-object answers (`heap_browseClassInstances`, `heap_getInstanceDetail`, `heap_getReferrers`, `heap_getDominatorTreeChildren`: the page shows the class row, the GC-root path or the tree's roots). A new note goes on this list.
- `MicroscopeView`/`MicroscopePage` constants are held to the frontend's pinned manifests `pages/src/router/profile-routes.json` and `global-routes.json` (`ProfileRouteManifestTest`, `McpUiLinkEnforcementTest.LinkTargets`). A link's query keys are held to `pages/src/router/link-params.json` (the params each linked page reads; `UiLinkRoutes.assertResolves` fails on an undeclared key); the frontend derives its param names from it (`FlamegraphLinkQuery`, `BaselineQuery`, `EventLinkQuery`), and `linkParams.spec.ts` pins it and checks the other direction: every linked page (or a module it imports) still reads each declared param. After changing a route run `npx vitest run -u` in `pages` to rewrite the manifests, then fix the Java constants the tests name.
- `McpUiLinkEnforcementTest` walks every advertised tool (`AdvertisedTools.all()`): each declares a non-null `uiLink` or is on `NO_PAGE` with a reason (11 today: `heap_listTables/describeTable/executeQuery`, the five `ide_`, `jfr_listTables/describeTable/executeQuery`).
- The flamegraph links are exact: `flamegraph-view` with event type, flags, `startEpochMs`/`endEpochMs` (the whole recording when none was asked, graphed over the same offsets) and `search`; a comparison adds `graphMode=DIFFERENTIAL&baseline=<id>`; a pair links `flamegraphs/differential?baseline=<id>`.
- **No exports** (owner decision): no tool writes a result to a file or a resource for the agent to fetch. Data goes to the agent in the answer, bounded and declared; the full view goes to the user as the `uiLink`.

### Hints and tracing
- **Weight is derived, never declared.** `McpToolWeight` (`LIGHT | MEDIUM | HEAVY`) is what an answer puts into the agent's conversation, as opposed to `cost` (what Jeffrey spends): HEAVY when the tool declares `maxResultSizeChars` (exactly the long documents — the exports, `jvm_threadDump`, `jfr_executeQuery`, `heap_getDominatorTreeRoots`; `McpToolsetAssemblerTest.LARGE_RESULTS` and `McpToolCatalogueTest` pin the set), LIGHT when `cost` is CHEAP, MEDIUM otherwise (`McpToolWeight.of`). It is not a `_meta` key. `McpToolCatalogue` (core) is the one static list of tool classes with their family prefix; `McpToolCatalogueTest` holds its names to exactly the advertised tools, so a class added to the assembler must be added there. `McpNextToolConformance` checks every emitted call's `weight` against the target spec. Markdown footers end each `Next:` line with ` [WEIGHT]`.
- `@McpToolMeta` gives every tool `cost` (`CHEAP | MODERATE | EXPENSIVE | SLOW`; SLOW exactly for the long-running tools that run on the call and stream progress, enforced by a core test) and optional `requires` (`HEAP_DUMP`, `HEAP_DUMP_INDEXED`, `HEAP_REPORTS`, `AUTO_ANALYSIS`, `TRACES`, `IDE_RUNNING`, `IDE_LINKED`, `CONNECTOR`), rendered as `_meta["jeffrey/cost"]` and `_meta["jeffrey/requires"]`; `maxResultSizeChars` is optional. A probe tool does not declare the requirement it probes (`ide_windows`, `connector_status`, `traces_overview`).
- A request's `params._meta.traceparent`/`tracestate` (W3C version 00, `McpTraceContext`) are recorded verbatim as attributes of the tool-call span, beside Jeffrey's own 64-bit ids; a malformed value is dropped and logged at debug by length only. The tracing library does not change.

### Resources
- Concrete: `jeffrey://server`, `jeffrey://diagnostics`, `jeffrey://profiles` (continued through the template `jeffrey://profiles{?cursor,limit}`). Templates, each offered only while its tool or family is served: `jeffrey://profile/{profileId}/summary`, `…/flamegraph/{eventType}`, `…/evidence`, and two documents no single tool returns — `…/schema` (every table and view of the profile database with its columns, the `fields` JSON note and event-type counts; served with the `jfr` family, URI built only by `McpResources.schemaUri`) and `…/findings` (the merged `McpFinding`s from **cached** auto-analysis, the container finding and capability gaps; `AutoAnalysisStatus` `COMPUTED | NOT_COMPUTED | CANNOT_COMPUTE`, `NOT_COMPUTED` offering `jvm_autoAnalysis {compute:true}`). A resource read never starts work; a missing resource is `-32602`.

### Investigation menu (`profiles_summary.investigationAreas`)
- The menu for an open question is server data, not skill prose: `InvestigationMenu.of(ProfileFacts, AdvertisedFamilies)` builds one `InvestigationOption {area, group, title, question, availability AVAILABLE|NEEDS_PREPARATION|NOT_RECORDED, weight, suggested, evidence, gap, remedy, nextTools, uiLink}` per `InvestigationArea` of the profile's `MenuSubject` (each `InvestigationGroup` carries its subject): a recording gets 16 areas in 4 groups (CODE, WAITING, JVM, OVERALL), a heap dump 10 in 3 (HEAP_CONTENTS, HEAP_RETENTION, HEAP_WASTE), a perf-counters snapshot none. At most 4 groups per subject and 4 areas per group — `InvestigationMenuTest.Catalogue` pins it, because a host asks one multi-select question per group with up to four options.
- Each area is an enum constant carrying its group, title, question, a sealed `AreaSource` (`Samples`, `JvmSectionsOf`, `Features`, `EventTypes`, `Rules`, `HeapReports`) that decides availability and the gap/remedy — and, through `preparation`, what has to be built first: only `HeapReports` has one (an unindexed dump → `heap_prepare` with no report; a missing stored report → `heap_prepare {report}`), which makes the area `NEEDS_PREPARATION` with that call as its `nextTools`, the one SLOW call a menu offers because there is nothing to read until it runs — an `AreaCalls` that builds its opening calls, an `AreaPage` that links the page it is seen on (null when not recorded; a flamegraph area the exact graph its export draws — event type, default weighting from `FlamegraphCatalog.weightedByDefault`, the whole recording — as `flamegraph_export`'s own uiLink; each `moreFlamegraphs` entry likewise), the families it needs (an area none of whose families is served is left out) and the auto-analysis topics that point at it. Add an area as a constant, never as a branch in the builder.
- CODE is one area per kind of sample, and each opens on its flamegraph: CPU and wall-clock on the graph alone, Allocation and Lock contention on the graph and then their table (`memory_allocations`, `blocking_overview`; an imported sample set's Allocation on the graph alone). There is no timeline area: an export of a whole recording offers `timeline_hotWindows` next. WAITING is Traces, Requests and calls, Database, I/O.
- Every recorded type with stacks that no area's `flamegraph_export` graphs — a second sampler of a kind, native allocation, method traces, custom events — is `profiles_summary.moreFlamegraphs` (`MoreFlamegraphs`, most samples first, at most `MAX_LISTED` with `omittedFlamegraphs`), each with its ready export: listed beside the menu, never an area, so the 4×4 menu holds.
- `ProfileFacts` holds only what `summary()` already read (panels from `FlamegraphCatalog`, the graphable types `flamegraph_list` reads, `JvmSections` shared with `ProfileCapabilityGaps`, disabled features, recorded event types, flagged findings) plus, for a heap dump, `HeapState` (dump present, index built, stored reports — `HeapDumpManager`'s `*Exists()` checks, no computation): the summary stays CHEAP and the menu runs nothing.
- Suggested: at most `MAX_SUGGESTED` (2) AVAILABLE areas — first WARNING/CRITICAL findings by topic (`InvestigationArea.forTopic`, unclaimed topics → RULE_FINDINGS), then a sample kind holding more than `DOMINANT_SAMPLE_SHARE` of the stack samples (wall-clock weighed only without CPU samples). It routes, never diagnoses. Heap areas are never suggested.
- The choice is the user's and is made in the client: the skills put a Pages table of the areas with data (`[↗ open](uiLink)`, Traces first when recorded, then the suggested ones) above the menu, then the menu as `AskUserQuestion` (Claude Code) or a table, offer at most two weighted follow-ups, and keep the Covered / Open leads / Not assessed ledger — stateless on the server.

### The code family: the repository's names in, the same names out
- Jeffrey never reads the application's repository. Code knowledge travels **in** as arguments the agent reads off its checkout — `framePrefixes` (the source tree's root packages, one name everywhere, as `jvm_exceptionSites` already took it), a class and method in source spelling, the methods a diff touched, a commit — and figures travel **out** keyed by the same names.
- `code_hotspots` (own methods by the cost **charged** to them: each sample to the deepest own frame on its stack, so library/JDK work lands on the method that asked for it; the charged figures add up to `chargedToOwnCode`; each row's `calledFrom` is the nearest own frame of another class above it on the stacks charged to it, so an own wrapper names the code that asked for its cost), `code_method` (one method or class across the recorded sample kinds — `flamegraphManager().eventSummaries()`, not every type with a stack — callers, callees, `ownCallers`, lines, tiers, exceptions under it, the busiest traced operations that run it) and `compare_methods` (compare family: named methods on both sides, `baselineScale`, `Movement` with `UNCHANGED` below `NEGLIGIBLE_SHARE_PCT`, `unlistedMovers`). All read the flamegraph's own per-stack records through `FlamegraphManager.codeAttribution(GraphParameters, CodeQuery)` → `CodeAttributionBuilder` (`core`, package `…core.profile.flamegraph.code`), so a method's figures and its frames in `flamegraph_export` agree; hidden-class frames are skipped as the differential skips them; inclusive counts a recursing method once per stack.
- `MethodRef` matches source spelling against runtime names (nested `Outer.Inner`/`Outer$Inner`, `lambda$m$N`, Kotlin `m$lambda$N`/`m$default`/`FileKt`/`Outer$m$1`, `access$m`); every answer lists `matchedFrames`. The other direction is `MethodRef.of(MethodKey)`: a named nested class in source spelling (`$`→`.`, kept for anonymous/generated segments), a javac lambda body by its enclosing method (`lambda$m$1`→`m`, not `static`/`new`) — every row naming an own method (`code_hotspots`, `code_callSites`, `compare_methods`' `unlistedMovers`) carries it as `reference` beside the runtime `frame`, and every offered `code_method` call uses it. A `NOT_SEEN` reference gets its nearest sampled methods (`CodeAnswers.nearest`: the method in the class named or one nested in it first, then that class's other methods, then namesakes elsewhere, compared in source spelling) — `code_method`'s `nearestFrames` (runtime names, pooled across every kind read) and `compare_methods`' `nearestReferences` (source spelling, to pass again; when the class's methods fill the list, its last slot goes to the hottest namesake elsewhere). `compare_methods` offers the retry only for `CodeAnswers.correction`: one source reference of that method, in the class named or one nested in it, across the complete pool of sampled methods — never from the capped suggestions, never a namesake in another class, never a choice between several. `framePrefixes` is bounded by `FramePrefixes` (32 entries of at most 200 characters), the one parser every tool taking it uses. A reference's flamegraph `search` (`CodeAnswers.search(MethodRef)`) lets each class dot match a `$` too (`[.$]`), so the source spelling finds the runtime frames. `NOT_SEEN` is a measurement with `nearestFrames`, never an empty answer. Without `framePrefixes`, `code_hotspots` uses `SuggestedPrefixes` (busiest non-library packages) and says `SUGGESTED`.
- `flamegraph_export` offers `code_hotspots` only from a whole-recording, thread-aggregated graph; `code_method` offers no export (the tree is guidance, the graph is its `uiLink`). Both keep the follow-up walk converging: the testapp walk is the longest (~1 020 calls), under `FollowUpWalk.MAX_CALLS` (1 500).
- Provenance: `recordings_analyzeFile` takes `commit` (7–64 hex, `SourceRevision.requireCommit`) and `dirty` (needs `commit`), written as tags `git.commit`/`git.dirty` on a fresh import only. `RecordingCommitResolver.revision` reads the tags first, then the profiled JVM's `jdk.InitialSystemProperty` (`git.commit`, `git.dirty`, `git.branch`); `profiles_get` reports `recordingCommit`, `recordingCommitSource` (`TAG | SYSTEM_PROPERTY`), `recordingDirty`, `recordingBranch`. `profile-run` passes `-Dgit.commit` and the import arguments.
- Runtime names ↔ code (`CodeSurfaceMcpTools`, code family): only Jeffrey's JDBC statements (and the JDK's socket/file/lock events, user JFR events) carry a stack — HTTP/gRPC exchanges, `TraceSpan`, `TraceScope`, `Notification` and pool events are `@StackTrace(false)`. `code_callSites` reads `ProfileEventStreamRepository.callSites` by `CallSiteReader`'s protocol (`DuckDBCallSiteQueries`, the `events` view so the pooled SQL comes back; one field's value read through a bound `$.<field>` path — field names checked as identifiers in `CallSiteQuery` — and `$.traceId`): the distinct stacks first, ordered by hash, each charged by `CallSiteBuilder.pathOf` to its `ownPath` (up to `MAX_OWN_PATH` own frames, deepest first — an own DB wrapper, then its callers); the path ids go back bound as two zipped lists, and the database aggregates per path and value, counting per trace before per site (`traces`, `perTraceMax`, `perTraceMedian`, the `MAX_EXEMPLARS` busiest, cut with `list_slice` — `[1:n]` reads as a named parameter). It then hands Java `onTotals` once (every event, its duration and the unattributed ones — events with no stack included — and how many sites and groups there are), and only the rows a `CallSiteSelection` asks for: `Sites(limit)`, the busiest sites across values (`code_callSites`' `limit`), or `Groups(limit, sitesPerGroup)`, the busiest values with their complete figures through `onGroup` and their busiest sites (`code_runtimeSurface`'s statements). Ranking happens in SQL, so a cap never changes a total, a group's figures or an omission count, and ties break by path — deterministic because the stacks arrive in hash order. Stacks are merged by path before the per-trace count, or one request issuing a statement through two stacks would count as two. Values are grouped whole in SQL and handed over cut to `CallSiteRow.MAX_GROUP_VALUE_CHARS` with their length and an MD5 that keys the site and the group, so a long SQL text never reaches the server whole and two statements alike for 200 characters stay apart; `repeatedPerTrace` from `REPEATED_PER_TRACE`; `JdbcCallSitesTest` pins the figures, the caps and the ties on DuckDB. a type without stacks is `NO_STACKS`. `code_runtimeSurface` places operations in code through the samples inside their spans (`SpanScope.Operation`, wall-clock first) — `CodeAttribution.entryPoints` (read only when the `CodeQuery` asks, `withEntryPoints()`) and charged `topMethods`, with `ownSamples` — and says it is inferred; an operation's entry point, from statement stacks or samples alike, is `EntryTrunk`'s: on the call path ≥ 90 % of its weight shares, the start of the longest run of consecutive own frames (every candidate on a tie, never a guess; a leading lambda skipped), so an own filter or worker loop above the handler and a callback below it are passed over, else each stack's outermost own frame; statements from call sites; attribute keys ordered developer-attached first. Neither is offered as a next call by an existing tool (`jdbc_overview` names `code_callSites` as guidance), so the walk is unchanged; the sweep calls `code_runtimeSurface`.
- The plugin's `build/plugin/shared/own-code.md` ("## Your own code") is the one account of deriving `framePrefixes` and reading runtime names; rendered into `optimize-code`, `code-insight`, `compare-jfr`, `regression-check`.

### Long work: synchronous, streamed progress
- The seven long tools (`recordings_analyzeFile`, `recordings_analyzeRecording`, `connector_download`, `connector_fetchFile`, `heap_prepare`, `heap_oql` with `includeRetainedSize`, `jvm_autoAnalysis` with `compute`) run their blocking manager **on the call** and stream `notifications/progress` over the response's SSE stream, then return the final result when the work finishes. `JeffreyToolRepository.isSlow` routes a `jeffrey/cost=SLOW` tool to `McpSyncResponse.streaming`; the tool reports progress through `McpCallContext.reportProgress(done, total, message)` (the `McpProgressSink`).
- There is no defer/poll engine: no `McpOperationRegistry`, no `operations_*` tools, no tasks extension, no `operationId`, no cancel RPC. The managers self-guard against concurrent duplicates (`ProfileRecordingsManager.once()` + `PipelineRunRegistry.startOrJoin`, `AutoAnalysisManagerImpl.inFlightLock`, the `HeapDumpSessionCache` per-dump lock), so a concurrent call of the same work joins the one run rather than starting a second.
- A long tool that fails raises a tool error (`isError`) carrying the reason; `recordings_status` reports a concurrently-running build's progress from `PipelineRunRegistry` (`READY`/`RUNNING`/`NOT_STARTED`/`INTERRUPTED`/`FAILED`), not from any retained in-memory operation.

### Skills: one catalogue, served two ways
- `McpSkillCatalogue` loads `classpath:mcp-skills/` once — the plugin's `skills/` directory, copied by `core`'s `copy-mcp-skills` execution — as raw bytes, and feeds both the prompts (`McpPromptRegistry`: each skill's body) and the `io.modelcontextprotocol/skills` extension (`skills/list`, `skills/get`, and each manifest file through `resources/read` as `skill://<name>/<path>`, digest `sha256` over the raw bytes). No second copy on the classpath, no hand-written frontmatter parser.
- `server/discover` declares the extension, and `McpServerInfo.capabilities.skills` is true, exactly when at least one skill loads (`McpSkillProvider.servesAny()`); `skills/*` answer every client, declared or not. An unknown skill or a `skill://` URI no manifest lists is `-32602`; `skill://` files never appear in `resources/list`.
- Frontmatter is strict YAML, parsed once (SnakeYAML `SafeConstructor`, YAML 1.2 core-schema resolver, no duplicate keys, no collection aliases). A skill that fails — a plain value holding `": "` included — is skipped with a warning, never repaired: quote the value in the `SKILL.md`. `McpSkillCatalogueTest` pins the thirteen plugin skills byte for byte.
- A skill is self-contained: a host resolves a relative reference against the skill's own directory and reads only what its manifest lists, so no link or backtick path in `skills/*/**/*.md` may leave its skill directory, and every target must exist (`check_skill_links` in `build/scripts/validate-agent-plugin.py`, and `McpSkillCatalogueTest.everyRelativeLinkResolvesInsideTheSameSkillsManifest`). Shared text is repeated inline — the tool-name prefix sentence is in each skill; only `report` keeps `references/tool-prefixes.md`, its own file. The same validator parses every `SKILL.md` frontmatter as YAML (PyYAML, strict loader); `--self-test` runs its broken fixtures.

### Tool hints are per tool, not per family
- Ten tools are not read-only, none changes an analysed profile: `recordings_analyzeFile`, `recordings_analyzeRecording`, `recordings_delete` (the only `destructiveHint`), `heap_prepare`, `connector_download`, `connector_fetchFile`, `ide_link`, `ide_open`, and the two slow reads that fill a cache, `jvm_autoAnalysis` (with `compute`) and `heap_oql` (with `includeRetainedSize`), which run synchronously and stream progress and are `idempotent`.
- `McpToolsetAssemblerTest` pins the write set **and the total tool count (114)**; the read-only count is repeated in prose in `DocsIndexPage.vue`, so change both when a tool is added or removed.
- Findings from judging tools (`jvm_autoAnalysis`, `jvm_container`) use `McpFinding` (id `category:subject`) so the same condition from two tools merges; `profiles_summary` carries `capabilityGaps` from `ProfileCapabilityGaps`.

### Artifacts are handed over, not parsed
- `connector_files` lists a session's artifacts (`gc.jvm-log`, `perf-counters.hsperfdata`, `.log`, `hs-jvm-err.log`); `connector_fetchFile` pulls one and answers with its **absolute path** — the agent greps it itself. Do not build a server-side log/crash parser or an `artifacts` table; both existed and were removed.
- No catalogue of fetched files: the path is deterministic (`profiles/<profileId>/artifacts/<name>`, or `artifacts/<workspace>/<project>/<session>/<name>` for a session with no recording). A file fetched before analysis is moved beside the profile on the next fetch. A repeat fetch reuses the copy already on disk (`alreadyHere`) rather than transferring it again — but the landing path is keyed by the file's name, not its fileId, so the session is listed again to resolve the fileId first; there is no in-memory catalogue that would answer a repeat fetch while the connector is down.
- Both path elements come off the wire (session id, file name): reduce each to a single path element and check the result is inside its base directory before writing.
- All `connector_` deadlines share one timer, `McpDeadlines`. No private schedulers.
- Known gap: `~/.jeffrey-microscope/artifacts/<workspace>/<project>/<session>/` has no retention.

### `connector_download` windows
- Whole session, or `startEpochMs`/`endEpochMs` → only the chunks covering the window (`ChunkWindow`: file *n* covers up to the start of *n+1*), or explicit `fileIds`. A partial download is tagged `origin.window` so `DownloadedSessionIndex` never reports it as the session's local copy. A whole-session copy already fully on disk is handed back for an identical whole-session call unless it may have changed (`DownloadKey.mayHaveChanged`): an open-ended window on an instance's newest session, or any part holding that session's newest recording, which may have been copied during the profiler's dump. There is no in-memory retained-download cache (the defer+poll engine is gone): a window or part is always transferred again on a repeat call, fail-safe (isolated temp dirs, fresh ids, never corruption). Contiguity: see `hub-repository.md`.
- Every chunk is selectable, the newest recording of the newest session included (it is on the volume whole; the download checks it on arrival). A chunk ends where the next begins; the newest ends one measured chunk length after its start (`ChunkWindow`, `RecordedSpan`), so a window past the data end selects nothing. Explicit bounds get the "No chunk … covers the window" refusal naming the session's start and data end; a window chosen in the question is asked again (`NO_CHUNK`).
- **Named windows: one `DownloadWindow` enum for the call and the form** (`connector/`): `WHOLE`, `LAST_MINUTES` (`minutes`, default 60), `STARTUP`, `LATEST`, `PEAK`, `BEFORE`/`AROUND` (`atEpochMs` + `minutes`), `CUSTOM` (bounds). Plain constants (the enum is an output type too); behaviour is a sealed `WindowRule` per constant, `takes`/`needsOneOf` sets drive `checkArguments` (chat only, before any network call; `window` with `fileIds`, or `minutes`/`atEpochMs` without a window, are refused). `resolve(given, Supplier<WindowSubject>)` → sealed `WindowResolution` (`Span` | `OneChunk` by fileId | `Whole` | `NotRetained` | `Refused`); rules that need no session (WHOLE, BEFORE, AROUND, CUSTOM) never call the supplier. The tool and the form answer go through the same `downloadResolved`: a call's `Refused` is an `IllegalArgumentException`, `NotRetained` the status `STARTUP_NOT_RETAINED` (connector_files + guidance, no download call); the form asks again with the problem first. `Download.chosen` (`ChosenWindow`) reports what a window picked and why; it travels beside `DownloadKey`, never in it.
- **Chunk facts are measured, never assumed** (`SessionChunks`): the chunk length (async-profiler `loop`) is the lower median spacing of consecutive chunk starts — no fixed length in code, tests, titles or docs; tests run at two lengths. STARTUP is kept while the oldest chunk starts ≤ one chunk length after the session; LATEST is the newest chunk with bytes; PEAK the largest **LZ4-compressed** chunk only (size on disk compares within one format; ties → most recent; none compressed → refused / not offered). The volume scheduler compresses every chunk but the newest of the newest session every `repository-jfr-compression.period` (default 1m).
- Follow-ups name exactly what was resolved, never the window again: whole → `window: WHOLE`; a span → its bounds; STARTUP/LATEST/PEAK → `fileIds:[id]` (a later LATEST could be a newer chunk and a second transfer).
- **The window question** (`DownloadWindowQuestion`, key `downloadWindow`): asked only when the client declared form elicitation, the call named no `window`, the key is whole-session (no window, no `fileIds`), nothing runs or is retained under it, no whole local copy exists (`mayAskForWindow`), and the session — read once by the preflight, which the transfer then reuses — runs longer than `jeffrey.microscope.mcp.connector.ask-window-over-duration` (default `PT1H`, measured from its start to the end of its recorded data) or holds more than `…ask-window-over-size` (default `1GB`, Spring `DataSize`). `PT0S`/`0B` mean always ask. Every other call downloads as before.
- Form: `window` — the `DownloadWindow` constants the session can offer (`choice(subject)`: no STARTUP once removed, no PEAK with nothing compressed, no LATEST without a chunk), UPPER values, default `LAST_MINUTES`, titled with the session's figures — plus `minutes` (default 60), `at`, `start`, `end` (`date-time`). Only the fields the chosen window takes are read; a malformed one is `Incomplete`, never thrown. Stretches are measured back from the end of the session's recorded data (`WindowSubject.end`); one reaching the start of a session a newer one has ended is the whole session. Answers are the sealed `WindowAnswer`: `Chosen(window, given)` → resolved like a call's window; `NotAnswered` (decline/cancel) → complete, non-error `NOT_DOWNLOADED` with `followUp`; `Incomplete` → asked again with the problem first.
- The question comes before the transfer; after the answer the transfer runs on the call and streams progress to completion. There is no tool-level single-flight: two concurrent `connector_download` calls for the same session each run their own transfer (fail-safe — isolated temp dirs, fresh ids, never corruption), rather than joining one. `connector_sessions`/`connector_files` never offer a download as a call (which part to bring is the user's choice): guidance only.

### Input requests (MRTR + form elicitation)
- Two questions only: the window above and `recordings_delete`'s confirmation (`DeleteConfirmation`, key `confirmDeletion`, one required boolean `confirm`, default false; `Confirmed | Withheld | Unanswered`). Withheld (unchecked, decline, cancel) → complete, non-error status `NOT_CONFIRMED` with its `reason`; no usable answer → asked again. The recording is validated before asking and again on the retry.
- Gate every question on `McpCallContext.canElicitForm()`: a client that did not declare form elicitation is never asked and its `inputResponses` are ignored; `destructiveHint` stays, and tool descriptions do not mention the question (the tool list is the same for every client). The bridge seals the tool name into the SDK's `requestState` (HMAC, `spring.ai.mcp.server.modern.request-state-secret`) and reconstructs the call from the retry's re-sent arguments; the SDK renders the `InputRequiredResult`.

### The `microscope` plugin (`jeffrey-agent-plugin/`)
- One set of skills, four manifests: Claude Code (`.claude-plugin/plugin.json`, configurable endpoint), Agent Plugins (`plugin.json` + `mcp.json`, fixed `localhost:8585`), Codex (`.codex-plugin/plugin.json`), Gemini (`gemini-extension.json`, `${JEFFREY_MCP_ENDPOINT:-…}`).
