## MCP server and plugin rules

### One AI integration, one direction
- Jeffrey never calls a model provider. No in-app assistant, chat, OQL helper, provider setting or secret storage — every earlier one is now a plugin skill over the MCP server. A feature that would put a model *inside* Jeffrey must be a skill or a tool instead.
- The endpoint is `POST /api/mcp` (`ExternalMcpController.PATH`), installation-wide, `profileId` as a tool argument. It is the only MCP endpoint and the only address: the old `/api/internal/…` alias and the loopback `claude-code` endpoint are gone — do not map a second path.
- Off only by `jeffrey.microscope.mcp.enabled` (read at startup). `hubs_` and `ide_` have their own switches (`…mcp.hubs.enabled`, `…mcp.ide.enabled`) because they reach outside the server. `…mcp.families` narrows what is advertised; `…mcp.preset` (`all|jfr|heap|hub`) picks a selection when that list is empty; `operations` must stay selected wherever a writer is — `ExternalMcpProperties` rejects an explicit list with `recordings`, `heap`, `hubs`, `ide` or `jvm` but no `operations`. Likewise `recordings` must stay selected wherever `hubs` is. Next-step hints to another family go through `AdvertisedFamilies.hint` (one `@Bean`), and `McpInstructions.text(AdvertisedFamilies)` describes only the advertised families.
- `McpRequestGuard` always rejects a `Host` outside `jeffrey.microscope.mcp.allowed-hosts` (loopback by default) and then a foreign `Origin` — both `403` with a reason naming the fix. `jeffrey.microscope.mcp.trust-forwarded-headers` (default false) takes host/scheme from the first `X-Forwarded-Host`/`X-Forwarded-Proto` for both checks, for a Jeffrey reachable only through a proxy. `jeffrey.microscope.mcp.token` is an optional bearer token checked last: when set, a missing or wrong `Authorization: Bearer` gets `401` + `WWW-Authenticate: Bearer` (constant-time compare, token never logged); when empty, any `Authorization` header is ignored, so manifests always send one. Refusal kinds are the sealed `McpRequestGuard.Refusal` (`Unauthorized`/`Forbidden`).

### The protocol lives in `mcp-protocol` (pure, boundary-tested); `mcp-server` adapts it
- **`jeffrey-microscope/mcp-protocol`** (package and JPMS module `cafe.jeffrey.microscope.mcp.protocol`) is MCP `2026-07-28` and nothing else: `McpRequestValidator`, the transport-neutral `McpDispatcher` (method table, every handler, result finishing, `input_required`, task rendering, error mapping; answers an `McpResponse(status, body)`, 202 for a notification), the tool/prompt/resource/completion SPI (`McpToolProvider`, `McpToolSpec`, `McpToolResult`, `CompositeToolset`, …), the tasks, skills and input-request extensions, the output-schema tooling (`McpSchemaGenerator`, `@McpOutputSchema`, `@McpNullable`, …), `McpCursor`, `McpText` (capping) and its own mapper (`McpJson`, configured as `shared/common`'s `Json`). It depends on Jackson and SLF4J only: its `ModuleBoundaryTest` fails on any `cafe.jeffrey.*` import outside its package, any `org.springframework.*` import, and any other `requires`. Its test-jar carries the generic helpers (`…protocol.testing`: `McpTestRequests`, `McpSchemaConformance`, `McpTestFeatures`).
- What is the server's comes in `McpDispatcherSettings`: the identity (`JeffreyMcpServer.IDENTITY`), the result limit (`McpToolOutput.MAX_CHARS`: text capped, structured content past it refused as the tool's error with `McpToolResult.OVERSIZED_STRUCTURED_CONTENT` — first inside the call by `ToolInvocation`, so the span fails, a resource read is `-32602` and a completion is empty; the dispatcher's own check covers task answers and non-reflective providers), an `McpFailurePolicy` (`JeffreyFailurePolicy`: unwraps `ToolInvocationException`, reads a client-error `JeffreyException` as `NOT_FOUND`/`CALLER_ERROR`, supplies "The tool failed inside Jeffrey…") and an `McpToolCallListener` (feeds `McpToolMetrics`).
- **`profiles/mcp-server`** (package `cafe.jeffrey.profile.mcp`) is Jeffrey's adapter: `AbstractMcpStreamableHttpController` (maps `McpResponse` onto a `ResponseEntity`), `ReflectiveToolset` (`@Tool`→MCP)/`ProfileScopedToolset`/`ToolMethodIndex`, `ToolInvocation` (the JFR span), the hints (`@McpToolMeta`, `McpToolCost`, `McpToolRequirement`, `@McpToolHints`, `JeffreyMetaKeys`), `McpToolNames` (family and title), `McpNextTool`/`McpFollowUp`, `finding/*`, `McpToolOutput`, `McpToolMetrics`. Its test-jar keeps `McpNextToolConformance` and `McpTestToolsets`. `McpToolProvider` cannot be sealed across modules, so `McpToolProviderImplementationsTest` (core) fails on any implementation but `ReflectiveToolset`, `ProfileScopedToolset` and `CompositeToolset`. Do not re-implement any of it in a controller, and do not put a Jeffrey or Spring type into `mcp-protocol`. Spring AI survives only for `@Tool`/`@ToolParam`.
- POST-only and stateless on purpose: `GET`/`DELETE` → 405, no `Mcp-Session-Id`, no SSE. Long work is an `operationId` polled through `operations_*`, or, for a client that declared tasks (`io.modelcontextprotocol/tasks`), a task after 5 s — never `notifications/progress`.
- **MCP `2026-07-28` only** (owner decision 2026-09-25, no backward compatibility). Every request carries `params._meta` (`io.modelcontextprotocol/protocolVersion`, `…/clientCapabilities`, optional `…/clientInfo`) plus the `MCP-Protocol-Version` and `Mcp-Method` headers, and `Mcp-Name` for `tools/call`, `prompts/get` (`params.name`), `resources/read` (`params.uri`) and `tasks/get|update|cancel` (`params.taskId`) — keyed on those three methods, never on a `tasks/` prefix. No `initialize`, no `ping`, no JSON-RPC batching, no handshake-era versions (`2024-11-05`…`2025-11-25`) — do not add any of them back. `McpRequestValidator` is the only place that checks this.
- Anything from the handshake era — a request without `_meta` or without `protocolVersion` in it (every `initialize`) — gets 400 `-32602` whose message and `data.supported` still name `2026-07-28`, so the client is told what to speak. `MCP-Protocol-Version` is compared with `_meta` *before* the version is judged: missing or disagreeing (and `Mcp-Method`/`Mcp-Name` likewise) → 400 `-32020`. Only when header and `_meta` agree on an unsupported version → 400 `-32022` with `data {supported, requested}`. A method needing an extension the client did not declare (`tasks/get`, `tasks/update` or `tasks/cancel` without the tasks extension) → 400 `-32021`; unknown method → 404 `-32601` (an `initialize` or `ping` that does carry modern `_meta` included, and `tasks/list` and `tasks/result`, which the tasks extension removed). `-32002` is never emitted (a missing resource is `-32602`).
- `server/discover` is the probe and must answer even when assembling the toolset would fail — nothing on that path may resolve the toolset (`McpCompletions.isAvailable()` reads configuration for that reason). Callers that only need "is Jeffrey up" (the plugin's `jeffrey-status.sh` hook, `validate-mcp.yml`'s readiness step) use it.
- Every result is finished by `McpResults`: `resultType`, `_meta["io.modelcontextprotocol/serverInfo"]`, and on `complete` results of `server/discover`, the list methods and `resources/read` the `ttlMs`/`cacheScope` cache hint. Structured results always: `tools/list` carries `outputSchema` wherever a tool has one and `tools/call` carries `structuredContent` whenever the result has it — there is no older-client text-only path.
- CI (`.github/workflows/validate-mcp.yml`) boots the jar, checks `tools/list` against `build/mcp/tools-list.snapshot.json` (`build/scripts/mcp-snapshot.py --check`, which also asserts the result envelope; the snapshot keeps each `outputSchema`'s content without descriptions and the values of every `jeffrey/*` hint, so schema drift fails CI — regenerate it from the packaged jar with `--url … > build/mcp/tools-list.snapshot.json`, never by hand), checks that the packaged jar's `skills/list` serves all ten skills and that discover declares `io.modelcontextprotocol/skills` (the only guard on the nested-jar skill loading), and runs the pinned MCP conformance suite twice against one baseline, `build/mcp/conformance-expected-failures.yml`: the active suite, and `server-stateless` (required by the 2026-07-28 requirement set, not in the active suite). The baseline holds only checks that call the suite's own fixtures (`test_*`, `test://*`). The `input-required-result-*` scenarios (in the 2026-07-28 requirement set) are not run: every check that exercises the server calls a suite fixture (`test_input_required_result_*`), and the two that do not (`unsupported-methods`, `validate-input`) pass; Jeffrey's own questions are pinned by unit tests. A baseline entry is one `<scenario>:<check-id>` with its reason; regenerate it from a real run, never by guessing.
- A tool's `title` is derived from its name by `McpToolNames.titleFor` (mcp-server); do not annotate it per method. `McpToolNames.familyOf` is the one reading of a tool's family.
- Tool descriptions say what the tool does, what it returns and what it is not for — at most 1 500 characters (400 per parameter), pinned by `McpToolsetAssemblerTest.noDescriptionExceedsTheHostCutoff`. Call order does not go in a description: it lives in `McpInstructions` (per advertised family) and in the skills.

### Results are typed records (Tier 3)
- **Structured output.** Every tool that answers a record declares `@McpOutputSchema(Record.class)` and returns `McpToolResult.of(record)` (text = the record's JSON) or `McpToolResult.of(markdown, record)` where the agent reads Markdown. 110 of 111 tools declare one; `ide_source` (a class's source text) is the only text-only tool, pinned by `McpToolSurfaceTest.TEXT_ONLY`. A tool with a schema must return structured content (`ToolInvocation`).
- **The generator is closed** (`McpSchemaGenerator`, mcp-protocol): it emits only `type`, `properties`, `required`, `additionalProperties`, `items`, `enum`, `description`, `minimum` — no `$ref`/`$defs`. Records become closed objects with every component required; `String`, booleans, integral and floating numbers, enums (their constant names), `List`/`Set`, `Map<String,T>` and `McpJsonObject` are the only other types. It refuses, with the path, `Object`, `JsonNode`, `Map<String,Object>`, `Instant`, `Duration`, `Optional`, arrays, raw/wildcard/generic types, recursive records, enums with bodies, a `toString()` or Jackson annotations, extra `get*`/`is*` methods and Jackson annotations on components — anything that would make Jackson write something the schema does not say. `@McpDescription` and `@McpMinimum` add the two optional keywords.
- **`McpJsonObject`** (`{"type":"object"}`) is the one open shape, sanctioned by component in `SpringAiToolConformanceTest.SANCTIONED_COMPONENTS`: `McpNextTool.arguments`, an operation's `result`, `McpFinding.evidence`. Type everything else; a new use needs a new sanctioned entry with its reason.
- **Null is explicit.** A component that can be absent is `@McpNullable` (schema `["t","null"]`, a nullable enum lists `null`) and is written as `null`, never omitted. Mark it only if the builder can leave it null; a component that is never null is pinned non-null by a test. `@McpNullableElement` marks nullable list/map elements (SQL NULL cells) and is refused on a bare component. A count the tool cannot know is null, never a false zero (`Figures` turns `-1`/blank sentinels into null).
- **Enums are UPPER_SNAKE constant names** on the wire, in outputs and in inputs alike, so a value round-trips; `ToolMethodIndex` binds `@ToolParamValues` inputs case-insensitively and rewrites them to the canonical spelling. `McpToolSurfaceTest` pins both directions. The one exception is `profiles_viewLink.view`, which takes Microscope route paths (echoed back verbatim, so they already round-trip) — pinned by `McpToolSurfaceTest.ROUTE_VALUED_INPUTS`; do not "fix" it to UPPER.

### Result conventions
- **Time:** every instant and window bound is UTC epoch milliseconds named `…EpochMs`, in inputs and outputs; durations carry a unit suffix (`…Ms`, `…Nanos`, never `…Millis`, no ISO strings). Windows are converted and checked only in `RecordingSpan`/`EpochWindow` (a refusal names the recording's own span). A comparison window is on the primary's clock, applied at the same offset into the baseline, and both landed windows are reported.
- **Ids:** a heap `objectId` is an unsigned decimal `String` in and out (`HeapObjectIds` parses at the boundary, 64-bit HPROF ids exceed JSON's 2^53). A well-formed but unknown id (object, operation, span, trace, event type, project) is a correctable tool error naming it; a status is only for a valid question that has no data.
- **Paging:** a result that can continue takes `cursor` and returns `hasMore` + `nextCursor` — one opaque `McpCursor` (versioned, fingerprinted to the filters; Jeffrey's codec is `JeffreyMcpServer.CURSOR`) through `OffsetPaging` or a keyset. No `offset` input, no prose paging line. A pure top-N keeps `limit` and declares its cut in the record.
- **`followUp`** (`McpFollowUp`: `nextTools` + `guidance`), built with `NextSteps.builder(advertised)`, replaces every prose next step. `nextTools` are `McpNextTool {tool, arguments, why}` with this answer's real ids, epoch-ms windows and cursors; `guidance` is advice that is not a call. Calls are family-gated (a withheld family is dropped), name only event types the profile recorded (`FollowUpCalls.recordedOnCpuEvent`/`recordedAllocationEvent`, else guidance), use `nextWhen(boolean, Supplier)` so nothing is built for a branch not taken, and never offer to rebuild a success: a SLOW or recomputing call (retry, `compute`, `retry:true`) is a `nextTools` entry only after FAILED, CANCELLED, NOT_RUN_YET or NOT_COMPUTED — otherwise guidance. A typed retry is an `McpNextTool` stored at registration (`McpOperationRegistry`). `McpFinding.nextTool` is an `McpNextTool`, gated with `McpFindings.reachable`. Tests check every emitted call with `McpNextToolConformance.assertFollowable`.
- **Markdown answers keep a footer.** A host may pass only the text to the model, so a tool whose text is Markdown or fixed-width text ends it with `LinkedOutput.footed(...)`: `Open in Microscope: <uiLink>` (+ its note) and a `Next:` line per call. The body is capped first (`McpToolOutput.cappedWithin`), so the footer always survives; `MarkdownFooters.assertRenderedFrom` checks it.
- **Statuses, not text:** "no data / not recorded / not computed / not run yet" is the same record with a `status` enum and a nullable `reason` (e.g. `CatalogueStatus`, `DashboardStatus`, `AutoAnalysisStatus`), with empty collections or null data — never a text-only return.
- **Declared cuts:** a bounded list keeps the rows that matter (`latest` for time series and dumps, `worst` for rankings, `GcDetailPages.Rows`), says which in `@McpDescription`, and reports an `omitted…` count (null when unknowable); several bounded tables share one budget through `FittingPage`. A cap that belongs to a lower layer is referenced from it (engine constants made public), never copied; a list cut by a cap it did not choose has a null omitted count.
- **Tests:** `StructuredAnswers` validates `structuredContent` against the generated schema (`McpSchemaConformance`) on the data path and every status path, checks each `nextTools` entry and resolves the `uiLink`.

### UI links: data for the agent, a link for the user
- Every answer whose subject has a Microscope page carries a `String uiLink` (absolute URL, no wrapper record) built with `UiLinks.view(profileId, MicroscopeView[, query])` or `UiLinks.page(MicroscopePage)` — never a hand-typed URL — including on status answers where the page exists. A `uiLinkNote` says only what the link still cannot reproduce — today: `traces_spanFlamegraphExport` and `traces_operationFlamegraphExport` (the graphs open in a modal / the operation's own panels), `traces_notifications` (no notifications page; it opens the operations), `compare_movements` (the page draws the graph, not the ranking), a differential whose baseline was read past the primary's window (`compare_flamegraph`, `compare_movements`), `heap_oql` (the console opens without the query), and the heap-object answers (`heap_browseClassInstances`, `heap_getInstanceDetail`, `heap_getReferrers`, `heap_getDominatorTreeChildren`: the page shows the class row, the GC-root path or the tree's roots). A new note goes on this list.
- `MicroscopeView`/`MicroscopePage` constants are held to the frontend's pinned manifests `pages-microscope/src/router/profile-routes.json` and `global-routes.json` (`ProfileRouteManifestTest`, `McpUiLinkEnforcementTest.LinkTargets`). A link's query keys are held to `pages-microscope/src/router/link-params.json` (the params each linked page reads; `UiLinkRoutes.assertResolves` fails on an undeclared key); the frontend derives its param names from it (`FlamegraphLinkQuery`, `BaselineQuery`, `EventLinkQuery`), and `linkParams.spec.ts` pins it and checks the other direction: every linked page (or a module it imports) still reads each declared param. After changing a route run `npx vitest run -u` in `pages-microscope` to rewrite the manifests, then fix the Java constants the tests name.
- `McpUiLinkEnforcementTest` walks every advertised tool (`AdvertisedTools.all()`): each declares a non-null `uiLink` or is on `NO_PAGE` with a reason (13 today: `operations_status/cancel`, `heap_listTables/describeTable/executeQuery`, the five `ide_`, `jfr_listTables/describeTable/executeQuery`).
- The flamegraph links are exact: `flamegraph-view` with event type, flags, `startEpochMs`/`endEpochMs` (the whole recording when none was asked, graphed over the same offsets) and `search`; a comparison adds `graphMode=DIFFERENTIAL&baseline=<id>`; a pair links `flamegraphs/differential?baseline=<id>`.
- **No exports** (owner decision): no tool writes a result to a file or a resource for the agent to fetch. Data goes to the agent in the answer, bounded and declared; the full view goes to the user as the `uiLink`.

### Hints and tracing
- `@McpToolMeta` gives every tool `cost` (`CHEAP | MODERATE | EXPENSIVE | SLOW`; SLOW exactly for the operation-backed tools, enforced by a core test) and optional `requires` (`HEAP_DUMP`, `HEAP_DUMP_INDEXED`, `HEAP_REPORTS`, `AUTO_ANALYSIS`, `TRACES`, `IDE_RUNNING`, `IDE_LINKED`, `HUB`), rendered as `_meta["jeffrey/cost"]` and `_meta["jeffrey/requires"]`; `maxResultSizeChars` is optional. A probe tool does not declare the requirement it probes (`ide_windows`, `hubs_list`, `traces_overview`).
- A request's `params._meta.traceparent`/`tracestate` (W3C version 00, `McpTraceContext`) are recorded verbatim as attributes of the tool-call span, beside Jeffrey's own 64-bit ids; a malformed value is dropped and logged at debug by length only. The tracing library does not change.

### Resources
- Concrete: `jeffrey://server`, `jeffrey://diagnostics`, `jeffrey://profiles` (continued through the template `jeffrey://profiles{?cursor,limit}`). Templates, each offered only while its tool or family is served: `jeffrey://profile/{profileId}/summary`, `…/flamegraph/{eventType}`, `…/evidence`, and two documents no single tool returns — `…/schema` (every table and view of the profile database with its columns, the `fields` JSON note and event-type counts; served with the `jfr` family, URI built only by `McpResources.schemaUri`) and `…/findings` (the merged `McpFinding`s from **cached** auto-analysis, the container finding and capability gaps; `AutoAnalysisStatus` `COMPUTED | NOT_COMPUTED | CANNOT_COMPUTE`, `NOT_COMPUTED` offering `jvm_autoAnalysis {compute:true}`). A resource read never starts work; a missing resource is `-32602`.

### Long work: an `operationId`, or a task
- One store: `McpOperationRegistry`, where operationId = taskId. `operations_*` and `OperationTasks` (the `io.modelcontextprotocol/tasks` view behind `tasks/get|update|cancel`) are two views of it, gated by the same `McpToolsetAssembler.reachable`; an unknown, expired or withheld taskId is `-32602` either way. No second store and no schema change — tasks are server-decided, so `tools/list` and the snapshot do not move.
- The wait is decided in `OperationAnswers` only. A client that declared tasks waits `BoundedJobs.TASK_WAIT_BUDGET` (5 s) and then gets a `CreateTaskResult`; every other client keeps the 45 s wait and the `operationId` text, which is why `operations_*` stays. The seven sites: `jvm_autoAnalysis`/`heap_oql` (`BoundedOperation`), `recordings_analyzeFile`/`recordings_analyzeRecording`, `hubs_download`/`hubs_fetchFile` (only the transfer await is capped; the hub preflight keeps its full budget), and `heap_prepare`, which does not wait — the task at once for a client that declared tasks, the `operationId` at once for any other — while preparation runs (a retained failed or cancelled run answers directly with its retry guidance).
- `server/discover` declares the extension (and `McpServerInfo.capabilities.tasks` is true) exactly when a family that starts an operation is served. `McpInstructions` stays one text for every client — discover is configuration-only — so it names both paths.
- A task's `ttlMs` is retention (1 h after it finishes), never a cache hint, and a running task outlives it; `pollIntervalMs` is 5 s. `tasks/update` ignores `inputResponses` (no mid-flight input yet). Two calls that join one operation share one taskId, so a `tasks/cancel` from either cancels both.
- The operation snapshot (`operations_status`) is typed: `OperationPhase`, UPPER state and kind, `…EpochMs`, `followUp`; its result renderers are `Function<V, ? extends Record>`. `BoundedOperation` has one record-form `run`, and a finished compute answers `withoutResult`.
- A finished task's `result` is the same text a waiting caller gets — each wait site registers one answer function and uses it on both paths. The one difference: a failed analysis is a task `completed` with `isError`, while a waiting `recordings_analyzeRecording` caller gets a non-error status document.

### Skills: one catalogue, served two ways
- `McpSkillCatalogue` loads `classpath:mcp-skills/` once — the plugin's `skills/` directory, copied by `core-microscope`'s `copy-mcp-skills` execution — as raw bytes, and feeds both the prompts (`McpPromptRegistry`: each skill's body) and the `io.modelcontextprotocol/skills` extension (`skills/list`, `skills/get`, and each manifest file through `resources/read` as `skill://<name>/<path>`, digest `sha256` over the raw bytes). No second copy on the classpath, no hand-written frontmatter parser.
- `server/discover` declares the extension, and `McpServerInfo.capabilities.skills` is true, exactly when at least one skill loads (`McpSkillProvider.servesAny()`); `skills/*` answer every client, declared or not. An unknown skill or a `skill://` URI no manifest lists is `-32602`; `skill://` files never appear in `resources/list`.
- Frontmatter is strict YAML, parsed once (SnakeYAML `SafeConstructor`, YAML 1.2 core-schema resolver, no duplicate keys, no collection aliases). A skill that fails — a plain value holding `": "` included — is skipped with a warning, never repaired: quote the value in the `SKILL.md`. `McpSkillCatalogueTest` pins the ten plugin skills byte for byte.
- A skill is self-contained: a host resolves a relative reference against the skill's own directory and reads only what its manifest lists, so no link or backtick path in `skills/*/**/*.md` may leave its skill directory, and every target must exist (`check_skill_links` in `build/scripts/validate-agent-plugin.py`, and `McpSkillCatalogueTest.everyRelativeLinkResolvesInsideTheSameSkillsManifest`). Shared text is repeated inline — the tool-name prefix sentence is in each skill; only `report` keeps `references/tool-prefixes.md`, its own file. The same validator parses every `SKILL.md` frontmatter as YAML (PyYAML, strict loader); `--self-test` runs its broken fixtures.

### Tool hints are per tool, not per family
- Eleven tools are not read-only, none changes an analysed profile: `recordings_analyzeFile`, `recordings_analyzeRecording`, `recordings_delete` (the only `destructiveHint`), `heap_prepare`, `hubs_download`, `hubs_fetchFile`, `operations_cancel`, `ide_link`, `ide_open`, and the two slow reads that fill a cache, `jvm_autoAnalysis` (with `compute`) and `heap_oql` (with `includeRetainedSize`), which run through a shared `BoundedOperation` (45 s wait, then an `operationId`; 5 s, then a task, for a client that declared tasks) and are `idempotent`.
- `McpToolsetAssemblerTest` pins the write set **and the total tool count (111)**; the read-only count is repeated in prose in `DocsIndexPage.vue`, so change both when a tool is added or removed.
- Findings from judging tools (`jvm_autoAnalysis`, `jvm_container`) use `McpFinding` (id `category:subject`) so the same condition from two tools merges; `profiles_summary` carries `capabilityGaps` from `ProfileCapabilityGaps`.

### Artifacts are handed over, not parsed
- `hubs_files` lists a session's artifacts (`gc.jvm-log`, `perf-counters.hsperfdata`, `.log`, `hs-jvm-err.log`); `hubs_fetchFile` pulls one and answers with its **absolute path** — the agent greps it itself. Do not build a server-side log/crash parser or an `artifacts` table; both existed and were removed.
- No catalogue of fetched files: the path is deterministic (`profiles/<profileId>/artifacts/<name>`, or `artifacts/<hub>/<project>/<session>/<name>` for a session with no recording). A file fetched before analysis is moved beside the profile on the next fetch. Fetch answers from disk before reaching for the hub.
- Both path elements come off the wire (session id, file name): reduce each to a single path element and check the result is inside its base directory before writing.
- All `hubs_` deadlines share one timer, `McpDeadlines`. No private schedulers.
- Known gap: `~/.jeffrey-microscope/artifacts/<hub>/<project>/<session>/` has no retention.

### `hubs_download` windows
- Whole session, or `startEpochMs`/`endEpochMs` → only the chunks covering the window (`ChunkWindow`: file *n* covers up to the start of *n+1*), or explicit `fileIds`. A partial download is tagged `origin.window` so `DownloadedSessionIndex` never reports it as the session's local copy. Contiguity: see `hub-repository.md`.
- On a live session the last finished chunk ends where the open chunk begins (`ChunkWindow.Selection.of`), never open-ended: a window lying only inside the chunk still being written selects nothing. Explicit bounds get the existing "No finished chunk … covers the window" refusal; a window chosen in the question is asked again (`NO_FINISHED_CHUNK`).
- **The window question** (`DownloadWindowQuestion`, key `downloadWindow`): asked only when the client declared form elicitation, the key is whole-session (no window, no `fileIds`), nothing runs or is retained under it, no whole local copy exists (`mayAskForWindow`), and the session — read once by the preflight, which the transfer then reuses — runs longer than `jeffrey.microscope.mcp.hubs.ask-window-over-duration` (default `PT1H`, measured to `finishedAt` or now) or holds more than `…ask-window-over-size` (default `1GB`, Spring `DataSize`). `PT0S`/`0B` mean always ask. Every other call downloads as before.
- Form: `window` (`lastHour` default | `lastMinutes` | `whole` | `custom`), `minutes` (1…session minutes, default min(15, max)), `start`/`end` (`date-time`, default the session's bounds). Stretches are measured back from the session's end; one reaching the start of a finished session is `Whole`. Answers are the sealed `WindowAnswer`: `Chosen` → a windowed key through the existing path; `Whole`; `NotAnswered` (decline/cancel) → complete, non-error status `NOT_DOWNLOADED` with `followUp`; `Incomplete` → asked again with the problem first. A malformed answer never throws — guard every Jackson conversion.
- The question comes before the transfer and before any task; after the answer it is the usual path (5 s then a task for a tasks client, 45 s + `operationId` otherwise). A RUNNING answer's `followUp` offers the `hubs_download` call with the exact `startEpochMs`/`endEpochMs` of its key (after `operations_status`), so a follow-up joins the same transfer instead of being asked again — keep it naming the key. `hubs_sessions`/`hubs_files` never offer a download as a call (which part to bring is the user's choice): guidance only.

### Input requests (MRTR + form elicitation)
- Two questions only: the window above and `recordings_delete`'s confirmation (`DeleteConfirmation`, key `confirmDeletion`, one required boolean `confirm`, default false; `Confirmed | Withheld | Unanswered`). Withheld (unchecked, decline, cancel) → complete, non-error status `NOT_CONFIRMED` with its `reason`; no usable answer → asked again. The recording is validated before asking and again on the retry.
- Gate every question on `McpCallContext.canElicitForm()`: a client that did not declare form elicitation is never asked and its `inputResponses` are ignored; `destructiveHint` stays, and tool descriptions do not mention the question (the tool list is the same for every client). No `requestState`: the retry's arguments name everything. `input_required` results carry `serverInfo` and never a cache hint (`McpResults.inputRequired`).

### The `microscope` plugin (`jeffrey-claude-plugin/`)
- One set of skills, four manifests: Claude Code (`.claude-plugin/plugin.json`, configurable endpoint), Agent Plugins (`plugin.json` + `mcp.json`, fixed `localhost:8585`), Codex (`.codex-plugin/plugin.json`), Gemini (`gemini-extension.json`, `${JEFFREY_MCP_ENDPOINT:-…}`).
- Skills are also served by the server — as MCP prompts and over the skills extension (see above); the profile catalogue as MCP resources; `McpInstructions` in `server/discover` — a client with no plugin still gets an account of how to use the tools.
- Client support is stated exactly, never stronger: Claude Code works on its v2 MCP runtime (`MCP_SDK_GENERATION=v2` where that is not the default); Codex from v0.147.0 with the global feature flag `[features] mcp_2026_07_28 = true` (or `codex --enable mcp_2026_07_28`), which applies to every HTTP server and which Codex marks as under development; Gemini CLI cannot connect until it speaks `2026-07-28` (its extension files stay for when it does); any other client works once it speaks `2026-07-28` over Streamable HTTP.
- Subagents do not survive the portable format: Codex TOMLs in `codex/agents/`, Gemini in `gemini/agents/` (hand-copied — Gemini rejects `disallowedTools`/`skills`/`color` frontmatter, accepts only `mcp_<server>_<tool>` patterns, and a Gemini subagent cannot dispatch another, so there is no Gemini `profile-lead`).
- The `report` skill is the evidence discipline every skill and agent writes to.
