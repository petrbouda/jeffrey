## Recording volume, hub jobs and file-download rules

Invariants of how the recording volume is laid out, kept and read — by the hub's jobs and by
Microscope reading it on an Azure file share. Each is a rule that was once broken; the "why" says
what went wrong. Do not re-derive these from the code.

### Who does what
- The volume is written by the provisioner (markers) and the profiled JVMs (recordings). Nothing reads a heartbeat: a session's order, whether it is its instance's newest and where its data ends all come from directory and file names. The **hub** runs its scheduler jobs on it — retention, stale-instance cleanup, compression — and serves only its own Storage and Scheduler pages. **Microscope** reads the volume on an Azure file share and makes the user's changes on it. The two never talk to each other: no gRPC, no REST between them, and no proto module. Do not add one back; both read the volume through `shared/volume`.

### One domain model per side
- Hub (`jeffrey-hub/hub-model`, `cafe.jeffrey.hub.model`) and Microscope (`jeffrey-microscope/microscope-model`) each map `shared/volume`'s layout types onto their **own** records: the hub in `FilesystemRepositoryStorage`, Microscope in `volume-client`'s `VolumeResponses`. A few records exist once per side on purpose (`RecordingSession`, `RepositoryFile`, `WorkspaceInfo`, `ProjectInfo`, …). `ModuleBoundaryTest` in `core-hub` and `core-microscope` fails on any import across the line.
- `shared/common` holds utilities and hub↔provisioner contract types only (`RemoteProject*`, `JeffreyLayout`, `ChunkWindow`). Never put a domain record there.
- `shared/volume` holds the volume's layout contract, read through the storage port `VolumeAccess` (`list`/`stat`/`read`/`open`; `read` stops at `MAX_READ_BYTES`, 1 MiB, because every profiled workload can write the volume) and changed through `WritableVolume` (`createDirectories`/`write`/`delete`); `FilesystemVolume` is the directory-tree backend (the hub's mount), `AzureFilesVolume` in `jeffrey-microscope/azure-files-volume` the Azure Files REST one: `ProjectTree` with `InstanceDirectory`/`SessionDirectory`/`SessionFile`, `ProjectSessions` (sessions with whether each is its instance's newest, `InstanceSummary`), `VolumeMarkers`, `WorkspaceMarker` and `VolumeWorkspace` (a root directory read as a workspace: its marker's name, or its id), `RecordingFormat` (with `theOneThatStays`, which serves the archive of two files sharing an id) and `FileRefusal` (the download refusals' sentences). Its types are volume-level, never a side's model. A listing's `VolumeEntry.createdAt` is `Optional` — an Azure NFS share lists no times — and `ProjectTree` stats a file whose listing has none; do not make it required again. The user's changes — a workspace created (`WorkspaceCreation`: the id already described, the name another workspace goes by), a session deleted (`SessionDeletion`), a workspace or project removed — have their rules once, in `VolumeChanges`, which Microscope applies on the share and the hub uses for its default workspace and its retention deletes; each side only words the refusal. Upkeep (retention, compression, single-file deletes) stays with the hub, on the `Path` that `FilesystemVolume.resolve` gives it.
- **The newest-file guard:** `RecordingSession.openRecording()` is the newest recording (by its name's timestamp) of an instance's **newest** session, and nothing else. Compression never touches it; the newest-session trim and the quota never delete it (the hub's `RecordingSession.trimmableRecordings()` is every recording but it). The compression job reads only each instance's two newest sessions (`RepositoryStorage.newestSessions`, `ProjectSessions.newestOfEachInstance`): an ended session is compressed by the run after a newer one starts. It is listed and downloadable like any file — the profiler writes a file whole when its loop ends, and Microscope checks a downloaded `.jfr` on arrival (`JfrChunkChain`: chunk sizes chain to the end of the file, no async-profiler placeholder header) and refuses a cut-short one. It must answer alike on both sides; the cases are pinned in each side's `RecordingSessionTest`.

### The volume is the only state
- No database, no reconciler, no `.pending` index, no cache: every read goes to the marker files the provisioner wrote (`.project-info.json`, `.instance-info.json`, `.session-info.json`) and the workspace's `.workspace-info.json` (read by `VolumeMarkers` in `shared/volume`, written whole through `WritableVolume.write` — scratch file, then rename — by `VolumeChanges`). A copy of the volume once had to be kept in step by two jobs and drifted from it; do not add one back.
- The one exception is Microscope's `RememberingVolume` (`volume-client`), over the share: it remembers only files that never change once written — the three provisioner markers — and only when they were there. Never a listing, a size or the workspace marker. A remembered file is forgotten when a listing of a directory above it stops showing it, when Microscope writes or deletes at or above it, and after `REMEMBERED_FOR`; a lookup by id confirms its memo with the listing it takes anyway (`ProjectSessions.stillListed`, `ProjectTree.instanceListing`: a real session or instance directory always holds its marker). The hub remembers nothing. Do not widen it to anything that can change.
- Every question asked of the share is a round-trip, so a session costs its marker and one listing of its directory (`SessionListing`, which answers its files and, from their names, where its data ends); nothing is looked at before it is read. Microscope runs a call's independent reads through `BoundedReadFanOut` (`ReadFanOut`, eight at a time; nested fan-outs run in order); the hub's is `ReadFanOut.sequential()`. `VolumeCallBudgetTest` pins the questions each read asks — update the counts with the change that moves them, never loosen it.
- Ids come from the volume: a workspace's id is its directory name (its reference id), a project's is the provisioner's `projectId`, an instance's and a session's are their directory names. Every lookup below the workspace carries `workspaceId` + `projectId` (`remote-client`'s `ProjectScope`), so a session is never searched for across the whole volume.
- A marker carries only what is read from it, plus its own id: `.project-info.json` the project's id, name, creation time and attributes; `.instance-info.json` and `.session-info.json` their id (equal to the directory name, which is what is used) and a creation time; `.session-info.json` also the machine's `zoneId`, because async-profiler writes `%t` in local time and `RecordingNameTimestamp` reads chunk names in that zone (UTC when absent — an older marker). Never write a location into a marker, absolute or relative — it is read from where the marker lies, and a written path once baked one container's mount point into a file another container read. A session's order in its instance is its start, read off its directory name — the provisioner names a session with a UUIDv7, whose top 48 bits are the start's epoch millis (`IDGenerator.timestampOf`), so name order is time order (`ProjectTree.OLDEST_NAMED_FIRST`); a name that carries no start falls back to the marker's `createdAt`. No ordinal is stored. The provisioner's `FileSystemRepositoryTest` pins each marker's field set.
- What a directory *is* has one predicate per level, reading its marker, all in `shared/volume`'s `ProjectTree`: `ProjectTree.at`, `instanceAt` and `sessionAt`. A directory whose marker is missing or unreadable is not that thing, for listings, lookups and counts alike — do not add a second check that looks only at the directory.
- There is no pinning: no session is exempt from retention or quota. A leftover `.retained` or `.heartbeat/` from an older release in a session directory is a hidden entry like any other and goes with the directory. Deleting a session deletes its instance directory too when nothing else is left in it (`VolumeChanges.deleteSession`): that is decided by **directories**, not by session markers, so a sibling whose marker is not written yet is never deleted with it. There is no EXPIRED state.

### No session status: order and names only
- There is no ACTIVE/FINISHED, no instance status, no `finishedAt` and no liveness: heartbeats were dropped because a file on the volume is whole except for the seconds of its dump, and everything a reader needs follows from order and names. A session is its instance's **newest** (no newer one has started there, so it may still grow) or it is ended. `ProjectTree.isNewest` reads only the siblings named after it, until one is a session (and any sibling whose name carries no start).
- "Newest" is per **instance**, never per project: with two instances per project the older instance's live session once read as finished and had the file its profiler was writing compressed and deleted. Each instance keeps its own newest file (pinned in both sides' tests).
- **Where data ends** (`lastDataAt`): the newest recording's start plus the measured chunk length — the lower median spacing of consecutive starts (`RecordedSpan` in Microscope); its start alone when there is one chunk; none without a recording. It replaces `finishedAt` for durations, windows ("last N minutes" is measured back from it), the session filter and an instance's or project's activity. The hub's retention ages a session by the same end (`RecordingSession.lastRecordingStart`, the newest recording's start, else the session's start).
- Two assumptions the order-only model rests on (owner decision): the profiler always runs with `loop` and `%t` in the file name, with a loop well under `session-retention` — a session is aged by its newest chunk's name, so a profiler that writes only at exit would be aged out while it runs; and an instance directory belongs to exactly one JVM — a second JVM in it would make the first one's session read as ended. Neither is guarded in code; do not add liveness back for them.
- Listing order is `ProjectTree.NEWEST_BY_NAME`, a constant, presentation only. Do not reintroduce a `FileInfoProcessor` strategy.

### Whether a file is a recording, and nothing more
- `RecordingFormat` (`shared/volume`) has exactly two constants, `JFR` and `JFR_LZ4`, because those are the only files the hub *does* anything to (timestamp from its own name via `TimestampResolver.RECORDING_NAME`, compression to LZ4 via the hub's `Compression.of(RecordingFormat)`). A format may be compressed exactly when it reads its timestamp from its own name; anything else (`app.pprof.lz4`) would change id and lose its original.
- `RecordingFormat.of(name)` is `Optional`; a file it is empty for (log, heap dump, pprof, `.jfr.N~` scratch) is listed and served as it lies: whole name as id, the volume's creation time as timestamp (`TimestampResolver.VOLUME`), not a recording. A recording's id drops its extension so one id names it and the archive it becomes (`SessionFile.idOf`).
- `core-hub` must not depend on `recording-storage-api` (Microscope's `ManagedFile`/`FileCategory`). Microscope classifies names itself in `RepositoryFiles`.
- Repository statistics is **one number** (bytes a project occupies): what the hub's last retention pass measured (`StorageOverviewCache`), shown on the hub's Storage page. Microscope never measures a share's projects. No per-kind buckets, no volume capacity (the RWX volume's `FileStore` never reports the PVC size).
- Whether a session `failed` (a newer session ended it before it wrote any data: zero bytes and not its instance's newest) is one rule, applied by `VolumeResponses.failed` for Microscope, `RecordingSession.isFailedEmpty` for the hub's retention and `sessionGrouping.ts` in the UI. The newest session is never failed.

### One level of the tree per call
- Workspaces → projects → instances → sessions → files, and each `remote-client` call answers one level: `DiscoveryClient` (workspaces, projects), `InstancesClient` (instances; one instance with a page of its sessions; a project's `activity`), `RepositoryClient` (one session with its files; the flat session listing), `FileStreamClient` (one file). A UI screen asks for the level it shows and nothing below it.
- **Finding a project reads its marker and nothing below it.** Every project-scoped request resolves its project (`ProjectManagerResolver` → `DiscoveryClient.project`), so that answer is `RemoteProjectResponse` off the marker alone; a project's last data and session count are `ProjectActivity` (`InstancesClient.activity`), read only by `ProjectManager.detailedInfo()` where they are shown. Resolving once read every instance and session of the project before each request did its own work.
- **Files travel only with one session — or with the instance page.** Every listing sends each session's file count and size and leaves `files` empty; Microscope's `RecordingSession` carries them as `SessionSize`, and a listed session's `files()` is empty. The one exception is the instance page's read (`InstancePage.newest`): it lists each of its sessions' directories for their count anyway, so it sends their files and `RecordingSessionList` seeds its reads from them (`sessionsCarryFiles`) — opening a session there asks for nothing.
- **The instance page is paged.** `GET …/instances/{id}?before=` answers the newest `InstancePage.PAGE_SIZE` sessions after the cursor and `hasOlder`; the UI's `LoadMoreFooter` reads the next page. Sessions named for their start (UUIDv7) are paged by name, so only the page's sessions are read (`ProjectSessions.instance(id, SessionPage)`) and the count is the instance's session directories; when a name carries no start every marker is read for the order.
- The flat session listing is for MCP's session search; Microscope's REST API has no project-wide session listing. One instance's sessions come from one read of that instance, never from filtering the project's listing, and the instance page takes both from one REST call (`GET …/instances/{id}`).
- An instance's last data comes from its **newest** session alone (`ProjectSessions.instances`): its count is the session directories of its listing, and only the newest by name is read — its marker and its listing (`ProjectTree.recordingStarts`, the chunk names, no stat). When names carry no start, every marker is read.

### A download is one file, whatever its kind
- One call, `FileStreamClient.streamFile(scope, sessionId, fileId)` (`VolumeFileStreamClient`), whatever the file is. What the caller does with the bytes is decided from the **listing** (`RepositoryFile.isRecordingFile()`, `RepositoryFiles.isArtifact`). Do not add a per-category download path.
- A file is refused, each **named with its reason** in `FileRefusal`'s words: a file the session does not hold (`NOT_IN_SESSION`), one no longer on the volume (`VANISHED` — looked up once more first, because the hub's compression job may have rewritten it under the same id), and an empty recording (`EMPTY_RECORDING`). The newest recording is served like any other; the receiver (`RemoteRecordingsDownloadManager.requireWhole`) refuses a `.jfr` that arrived cut short and deletes nothing on the volume. `.jfr.N~` is served like any file; Microscope declines to ask for it.
- **The name travels with the bytes**: the receiver writes what arrived (`FileStreamClient.TransferredFile`, which reduces the name to one path element in its compact constructor).

### A download is an unbroken run of chunks
- Files are downloaded one at a time, in parallel, and kept as several files; nothing joins them. The recording carries one start/end across its files, so a skipped chunk leaves a silent hole. `RemoteRecordingsDownloadManager` refuses a gapped selection and an id the session does not hold; `remote_download` refuses naming the missing chunk; the UI mirrors it in `chunkSelection.ts`. The predicate is `ChunkWindow.Selection.contiguous()` in `shared/common` — do not add a fourth copy. A window selection cannot be gapped; only `fileIds`/checkbox picks need checking.

### Compression belongs to the compression job only
- Never compress on a read path: it once rewrote the repository mid-read and the client wrote LZ4 bytes under a `.jfr` name.
- `Compression.compress` writes to a scratch file beside the target (`VolumePath.scratchName`) and renames — an archive appears whole or not at all. Everything downstream (delete-on-archive-exists, a download handing over the archive) rests on it. Whether a format is an archive is `RecordingFormat.isArchive()`, not the extension.

### Microscope makes the user's changes, never upkeep
- Microscope's remote is an `AzureFilesAddress` (`RemoteInfo.address`), served by `volume-client`'s `Volume*Client`s over a `VolumeSource`, built by `AzureFilesClientsFactory`. They implement the `remote-client` interfaces.
- The user's changes (create/delete workspace, delete project, delete session) go through `VolumeChanges` on the source's `WritableVolume`. Retention, compression and every other upkeep stay with the hub's jobs on the volume — never add them to Microscope.
- `azure-files.read-only=true` (`AzureFilesAddress.readOnly`, not part of `identity()`) makes `VolumeSource.writable` refuse every change; the UI hides them (`RemoteResponse.readOnly`, read on project pages through `@remote/composables/useRemoteReadOnly`), `remote_status` reports `readOnly`, and `RemoteWorkspaceManager.delete` refuses before its best-effort local cleanup.
- The remote is declared in configuration only (`ConfiguredRemoteProperties`), read at startup and never stored; no REST call or MCP tool connects, changes or disconnects it. A SAS token is never logged: it stays in `ConfiguredRemoteProperties.sasToken()`, and only its rights (`SasPermissions`) are ever logged. `AzureFilesAddress` takes a bare `https://host` endpoint and refuses a path, query or user info without quoting it, so a pasted SAS URL cannot reach a log or an answer.

### Nothing on the hub reads a recording
- No JFR parser, no replay stream, no event-activity scan, no session-environment reader. Pull the chunks covering a window into Microscope instead. Never add MCP to the hub.

### Scheduler
- No descriptor hierarchy, no `JobContext`: a job reads its params from its `JobConfig` at construction and `execute()` takes nothing. Every job bean lives in `configuration/SchedulerConfiguration`; `JobLocks` is the one per-job lock the tick and `ManualJobRunner` both take.
- One pool (`PeriodicalScheduler`, `jeffrey.hub.scheduler.fan-out-pool-size`): every job runs per project, so there is no execution level or executor group. Two jobs: `ProjectRetentionJob` and `RepositoryCompressionProjectJob`. Retention is **one pass per project**: the sessions are listed once with their files and the sealed `RetentionRule`s run over that `ProjectRetentionPass` in order (data age + per-instance cap; live trim of each instance's newest session; quota — ended sessions oldest first, then the newest sessions' old files; instances with no session left past the retention window), every deletion going through the pass so later rules and the storage figure see what is left. None of them deletes the newest-file guard's file. Compression (`RepositoryCompressionProjectJob`) covers each instance's two newest sessions — an older one was compressed while it was among them — and skips the guard's file. The storage overview is published from that pass into `StorageOverviewCache`; do not add a second walk of the repository for it, nor a separate cleaner job.
- The hub's managers (`WorkspacesManager` → `WorkspaceManager` → `ProjectsManager` → `ProjectManager` → `RepositoryStorage`) exist to feed the jobs: keep only what a job, the default workspace or the Storage and Scheduler pages call.
