## Hub repository and file-download rules

Invariants of how the hub stores, lists and serves a session's files. Each is a rule that was
once broken; the "why" says what went wrong. Do not re-derive these from the code.

### One domain model per side
- Hub (`jeffrey-hub/hub-model`, `cafe.jeffrey.hub.model`) and Microscope (`jeffrey-microscope/microscope-model`) each map the proto in `shared/hub-api` onto their **own** records (`ProtoMappers` on the hub, `ClientProtoMappers` in `remote-client` — `session(...)` is the one decoding of a session and its files). Ten records exist once per side on purpose (`RecordingSession`, `RepositoryFile`, `RecordingStatus`, `WorkspaceInfo`, `ProjectInfo`, …). `ModuleBoundaryTest` in `core-hub` and `core-microscope` fails on any import across the line.
- `shared/common` holds utilities and hub↔provisioner contract types only (`RemoteProject*`, `JeffreyLayout`, `ChunkWindow`). Never put a domain record there.
- `shared/volume` holds the volume's layout contract, read through the storage port `VolumeAccess` (`list`/`stat`/`read`/`open`; `read` stops at `MAX_READ_BYTES`, 1 MiB, because every profiled workload can write the volume) and changed through `WritableVolume` (`createDirectories`/`write`/`delete`); `FilesystemVolume` is the directory-tree backend, `AzureFilesVolume` in `jeffrey-microscope/azure-files-volume` the Azure Files REST one: `ProjectTree` with `InstanceDirectory`/`SessionDirectory`/`SessionFile`, `ProjectSessions` (sessions with their liveness, `InstanceSummary`/`InstanceState`), `VolumeMarkers`, `WorkspaceMarker` and `VolumeWorkspace` (a root directory read as a workspace: its marker's name, or its id), the liveness classes, `RecordingFormat` (with `theOneThatStays`, which serves the archive of two files sharing an id) and `FileRefusal` (the download refusals' sentences). Its types are volume-level, never a side's model: the hub maps them in `FilesystemRepositoryStorage`, Microscope in `volume-client`'s `VolumeResponses`. A listing's `VolumeEntry.createdAt` is `Optional` — an Azure NFS share lists no times — and `ProjectTree` stats a file whose listing has none; do not make it required again. The user's changes — a workspace created (`WorkspaceCreation`: the id already described, the name another workspace goes by), a session pinned or deleted (`SessionDeletion`), a workspace or project removed — have their rules once, in `VolumeChanges`, used by the hub and by Microscope alike; each side only words the refusal. Upkeep (retention, compression, single-file deletes) stays with the hub, on the `Path` that `FilesystemVolume.resolve` gives it.
- `RecordingSession.openRecording()` (which chunk the profiler still holds open) must answer alike on both sides; the same three cases are pinned in each side's `RecordingSessionTest`.

### The volume is the hub's only state
- No database, no reconciler, no `.pending` index, no cache: every call reads the marker files the provisioner wrote (`.project-info.json`, `.instance-info.json`, `.session-info.json`) and the hub's own `.workspace-info.json` (read by `VolumeMarkers` in `shared/volume`, written whole through `WritableVolume.write` — scratch file, then rename — by `VolumeChanges`). A copy of the volume once had to be kept in step by two jobs and drifted from it; do not add one back.
- Ids come from the volume: a workspace's id is its directory name (its reference id), a project's is the provisioner's `projectId`, an instance's and a session's are their directory names. Every request below the workspace carries `workspace_id` + `project_id` (`GrpcLookups`), so the hub never searches the whole volume for a session.
- A marker carries only what the hub reads, plus its own id: `.project-info.json` the project's id, name, creation time and attributes; `.instance-info.json` and `.session-info.json` their id (equal to the directory name, which is what the hub uses) and a creation time; `.session-info.json` also the machine's `zoneId`, because async-profiler writes `%t` in local time and `RecordingNameTimestamp` reads chunk names in that zone (UTC when absent — an older marker). Never write a location into a marker, absolute or relative — the hub reads it from where the marker lies, and a written path once baked one container's mount point into a file another container read. A session's order in its instance is its creation time; no ordinal is stored. `FileSystemRepositoryTest` pins each marker's field set.
- What a directory *is* has one predicate per level, reading its marker, all in `shared/volume`'s `ProjectTree`: `ProjectTree.at`, `instanceAt` and `sessionAt`. A directory whose marker is missing or unreadable is not that thing, for listings, lookups and counts alike — do not add a second check that looks only at the directory.
- A session pinned against retention is a `<session>/.retained` flag file. Deleting a session deletes its instance directory too when nothing else is left in it (`VolumeChanges.deleteSession`): that is decided by **directories**, not by session markers, so a sibling whose marker is not written yet is never deleted with it. There is no EXPIRED state.

### Session status is derived when read, by the hub
- `SessionLiveness` (`shared/volume`, read through `HeartbeatReader`) decides it from the session's own files, in order: the `finished` marker; a newer session in the same instance (finished at the last heartbeat, else at the next session's start); a stale heartbeat (finished at it); an unreadable liveness file (still recording); the startup grace; and past it, finished at its start with `heartbeatMissing`. Thresholds are `jeffrey.hub.liveness.*`. It lives in `shared/volume` so that every reader of a volume answers alike, but for a session served by the hub the hub decides it, because compression, retention and downloads need the same answer; do not send heartbeats to Microscope to decide it there. Only a volume source (below), which has no hub, decides it in Microscope, with the same `SessionLiveness`.
- A session's status never comes from its position in the project's listing. With two instances per project the older live session once read as FINISHED and had the file its profiler was writing compressed and deleted (`everyUnfinishedSessionIsLiveWhateverItsPosition` pins it).
- An instance's status follows from its sessions (`ProjectSessions.instances`/`instance`, `InstanceSummary.state()`): PENDING with none, ACTIVE while its newest records, FINISHED otherwise. A project with no session has no status and is sent as `RECORDING_STATUS_UNSPECIFIED`.
- Listing order is `ProjectTree.NEWEST_BY_NAME`, a constant, presentation only. Do not reintroduce a `FileInfoProcessor` strategy.

### The hub reports whether a file is a recording and nothing more
- `RecordingFormat` (`shared/volume`) has exactly two constants, `JFR` and `JFR_LZ4`, because those are the only files the hub *does* anything to (timestamp from its own name via `TimestampResolver.RECORDING_NAME`, compression to LZ4 via the hub's `Compression.of(RecordingFormat)`). A format may be compressed exactly when it reads its timestamp from its own name; anything else (`app.pprof.lz4`) would change id and lose its original.
- `RecordingFormat.of(name)` is `Optional`; a file it is empty for (log, heap dump, pprof, `.jfr.N~` scratch) is listed and served as it lies: whole name as id, the volume's creation time as timestamp (`TimestampResolver.VOLUME`), `is_recording=false`. A recording's id drops its extension so one id names it and the archive it becomes (`SessionFile.idOf`).
- `core-hub` must not depend on `recording-storage-api` (Microscope's `ManagedFile`/`FileCategory`). Microscope classifies names itself in `ClientProtoMappers.file` and `RepositoryFiles`.
- Repository statistics is **one number** (bytes a project occupies): what the last retention pass measured (`StorageOverviewCache.projectSize`), sent as `ProjectInfo.size_bytes` and absent before the first pass — never re-measured on request, and the hub has no statistics RPC. No per-kind buckets, no volume capacity (the RWX volume's `FileStore` never reports the PVC size), no `hs_err` detection on the hub.
- Whether a session `failed` (finished with no data, not for a missing heartbeat) is the hub's call, sent on `RecordingSession.failed`.

### One level of the tree per call
- Workspaces → projects → instances → sessions → files, and each call answers one level: `ListWorkspaces`; `ListProjects`/`GetProject`; `ListInstances`; `GetInstance` (one instance and its sessions); `GetSession` (one session and its files); `DownloadFile`. A UI screen asks for the level it shows and nothing below it.
- **Files travel only with `GetSession`.** Every listing (`ListSessions`, `GetInstance`) sends each session's `file_count` and `size_bytes` (`ProtoMappers.sessionHeader`) and leaves `files` empty; Microscope's `RecordingSession` carries them as `SessionSize`, and a listed session's `files()` is empty. The UI fetches a session's files when it is opened (`RecordingSessionList`, the timeline drawer). Before this, opening the timeline sent every file of every session twice.
- `ListSessions(project, filter)` is the one flat listing, for MCP's session search and the instances timeline; Microscope's REST API has no project-wide session listing. One instance's sessions come from `GetInstance` (`instanceWithSessions`, one read of the instance for both), never from filtering the project's listing, and the instance page takes both from one REST call (`GET …/instances/{id}`).
- Project and instance status come from each instance's **newest** session alone (`ProjectSessions.instances`): a newer session is what finishes the one before it, so an older session's liveness files are never read for a status. The session count is the instance's session markers.

### A download is one file, and the hub does not care what kind
- One RPC, `DownloadFile(workspaceId, projectId, sessionId, fileId)` (`file_download_service.proto`, `FileDownloadGrpcService`, `FileStreamClient.streamFile`) over one `RepositoryStorage.file(sessionId, fileId)`, which returns the sealed `FileLookup` (`Found(path)` or a `Refused` with its `reason()`), never throws a refusal. What the caller does with the bytes is decided from the **listing** (`RepositoryFile.isRecordingFile()`, `RepositoryFiles.isArtifact`), never from which endpoint answered. Do not add a per-category download path.
- The hub refuses, each **named with its reason** and sent as INVALID_ARGUMENT: a file the session does not hold (`NotInSession`), the chunk still being written (`StillWriting`, `RecordingSession.isOpen`), one no longer on the volume (`Vanished` — at lookup or at open; looked up once more because the compression job may have rewritten it), and an empty recording (`EmptyRecording`), each worded by `FileRefusal` so a volume source refuses in the same sentence. `.jfr.N~` is served like any file; Microscope declines to ask for it.
- **The name travels with the bytes**: `DataChunk.filename` on the first chunk; the receiver writes what arrived (`FileStreamClient.TransferredFile`, which reduces the name to one path element in its compact constructor).

### A download is an unbroken run of chunks
- Files are downloaded one at a time, in parallel, and kept as several files; nothing joins them. The recording carries one start/end across its files, so a skipped chunk leaves a silent hole. `RemoteRecordingsDownloadManager` refuses a gapped selection and an id the session does not hold; `remote_download` refuses naming the missing chunk; the UI mirrors it in `chunkSelection.ts`. The predicate is `ChunkWindow.Selection.contiguous()` in `shared/common` — do not add a fourth copy. A window selection cannot be gapped; only `fileIds`/checkbox picks need checking.

### Compression belongs to the compression job only
- Never compress on a read path: it once rewrote the repository mid-read and the client wrote LZ4 bytes under a `.jfr` name.
- `Compression.compress` writes to `.<name>.<uuid>.tmp` beside the target and renames — an archive appears whole or not at all. Everything downstream (delete-on-archive-exists, `file()` handing over the archive) rests on it. Whether a format is an archive is `RecordingFormat.isArchive()`, not the extension.

### A volume source makes the user's changes, never upkeep
- Microscope can reach the volume with no hub: a remote whose address is `AzureFilesAddress` (sealed `RemoteAddress`, beside `HubAddress`) is served by `volume-client`'s `Volume*Client`s over a `VolumeSource`, built by `RemoteClientsFactory`/`AzureFilesClientsFactory`. They implement the same `remote-client` interfaces as the `Grpc*Client`s, and answer as the hub would: one level per call, files only for one session, the same download refusals in the hub's wording, `failed` by the hub's rule.
- The user's changes (create/delete workspace, delete project, delete/pin session) go through `VolumeChanges` on the source's `WritableVolume`, with the hub's refusals in its words. Retention, compression and every other upkeep stay with a hub running on the volume — never add them to a volume source.
- `azure-files.read-only=true` (`AzureFilesAddress.readOnly`, not part of `identity()`) makes `VolumeSource.writable` refuse every change; the UI hides them (`RemoteResponse.readOnly`, read on project pages through `@remote/composables/useRemoteReadOnly`), `remote_status` reports `kind` and `readOnly`, and `RemoteWorkspaceManager.delete` refuses before its best-effort local cleanup.
- The remote is declared in configuration only (`ConfiguredRemoteProperties`), read at startup and never stored; no REST call or MCP tool connects, changes or disconnects it. A SAS token is never logged: it stays in `ConfiguredRemoteProperties.sasToken()`, and only its rights (`SasPermissions`) are ever logged. `AzureFilesAddress` takes a bare `https://host` endpoint and refuses a path, query or user info without quoting it, so a pasted SAS URL cannot reach a log or an answer.

### Protos ship together
- Hub and Microscope are one release: a removed field's number is reused and survivors renumbered, no `reserved`. If versions ever diverge, flip this rule.

### Nothing on the hub reads a recording
- No JFR parser, no replay stream, no event-activity scan, no session-environment reader (`SessionEnvironmentReader` lives in `remote-client` and parses in Microscope). Pull the chunks covering a window into Microscope instead. Never add MCP to the hub.

### Scheduler
- No descriptor hierarchy, no `JobContext`: a job reads its params from its `JobConfig` at construction and `execute()` takes nothing. Every job bean lives in `configuration/SchedulerConfiguration`; `JobLocks` is the one per-job lock the tick and `ManualJobRunner` both take.
- One pool (`PeriodicalScheduler`, `jeffrey.hub.scheduler.fan-out-pool-size`): every job runs per project, so there is no execution level or executor group. Two jobs: `ProjectRetentionJob` and `RepositoryCompressionProjectJob`. Retention is **one pass per project**: the sessions are listed once with their files and the sealed `RetentionRule`s run over that `ProjectRetentionPass` in order (age + cap, live trim, quota, stale PENDING instances), every deletion going through the pass so later rules and the storage figure see what is left. The storage overview is published from that pass into `StorageOverviewCache`; do not add a second walk of the repository for it, nor a separate cleaner job.
