## Test Rules

### Java
- JUnit 5, `@Nested` classes to group by method or scenario; Mockito for collaborators.
- `@DuckDBTest` (from `shared/test`) for database integration tests — each test gets an isolated DuckDB.
- Time via `Clock.fixed(instant, zone)`; never the real clock.
- Async/polling assertions with Awaitility: `await().atMost(5, SECONDS).untilAsserted(...)`; never `Thread.sleep` loops.
- Naming: `{ClassUnderTest}Test` / `{Feature}IntegrationTest`; method names describe the scenario.
- A recording volume in a test is laid down with `VolumeWriter` (`shared/test`); real recordings come from `RecordedSession` beside it — four consecutive 15-minute async-profiler chunks of one real session, with each chunk's CPU-sample, allocation, park and monitor-enter counts pinned (as `jfr summary` reads them), laid out plain (`writeTo`) or as the hub's compression job leaves them (`writeAsTheHubLeavesIt`). Pin what an answer must hold from those figures, never "something came back".
- Realistic recordings: `shared/test` (beside `RecordedSession`, under `cafe/jeffrey/test/recording/persons/`) holds two runs of one service under load, copied byte for byte from `jeffrey-recordings` (`jeffrey-persons-direct-serde-cpu.jfr.lz4`, `…-dom-serde-cpu.jfr.lz4`: async-profiler CPU, wall, alloc and lock with `jfrsync`, ~40k CPU and ~4–5M wall samples each). Each file is two chains of chunks that overlap in time and number their event types differently: the JDK's own (chunks 0–1) and async-profiler's (2–4). `PersonsRecording` pins each run's `Counts` as `jfr summary` reads them **per chunk** (over a whole such file it mislabels the profiler's types) — wall-clock as events and as samples (each event's `samples` field summed) — plus every chunk's start, the run's span (earliest start to latest end, not the durations added up) and each profiler chunk's own counts. They are tested at three levels: `JfrParserRealisticRecordingTest` (`raw-jfr-parser`: chunks, span, event types, LZ4 against plain, disassembly), `JfrRecordingEventParserRealisticTest` (`profile-management`: exact events and samples per type, the same however the run is read — archive, plain, split or as it lies, as chunk files — and what each chain holds; an equivalence is also checked against the pinned counts, since two readings that lost the same events still agree), and end to end in `core-microscope`, where `PersonsVolumeMicroscope` lays each run down twice: as its one file (pod `persons-0`) and as async-profiler's three chunks cut by `JfrFileChunks` (pod `persons-1`), named by when each began, its header checked against the pinned start, compressed as the hub leaves them. `PersonsRecordingsIntegrationTest` holds figures, the walk, the sweep, the chunked sessions (the chunks add up to the file they were cut from; LAST_MINUTES, PEAK, a window inside one chunk, a gapped pick) and the DOM-vs-direct comparison to them. A recording added (one with traces next) gets a constant with its figures, and the walk's pinned set grows with what it holds.
- The walk and the sweep are `FollowUpWalk` and `ToolSweep`, shared by every booted volume: seed the walk with the user's choices (a download — no answer suggests one), pin the tools it reaches, and build the profiles first so the set does not depend on test order.
- Microscope booted whole over a local connector: `BootedMicroscope` is the boot and the helpers; every class extending `LocalVolumeMicroscope` (`core-microscope`) shares one `@SpringBootTest` (real port, real DuckDB, `applicationClock` fixed by `@TestBean`) over a volume holding `RecordedSession` with a GC log and crash file, a session cut short and one to delete, and drives it over HTTP as an agent (`POST /api/mcp`) and the UI (`/api/internal/**`) do through `MicroscopeClient`, which checks every structured answer against its advertised `outputSchema`. `MicroscopeLocalConnectorIntegrationTest` (status, sessions, windows, refusals, UI pages), `McpFollowUpWalkIntegrationTest` (follows every call any answer suggests, from `connector_status` on; the tools it reaches are pinned), `McpToolSweepIntegrationTest` (every tool callable with the profile alone answers or refuses in a sentence; a recording refuses exactly the heap tools but `heap_status`), `McpAnswerFiguresIntegrationTest`, `McpCompareIntegrationTest` and `ConnectorArtifactsIntegrationTest`; `MicroscopeReadOnlyLocalConnectorIntegrationTest` boots a second, read-only one. They are the one place the chain volume → download → parser → DuckDB → answer runs unmocked: add a scenario there rather than another mock of a layer below the tools. A suggestion that leads nowhere or a tool that fails inside on a real profile fails here first. Their volume and home live under `target/local-connector-it/`.
- Tests that pin a count or a set repeated elsewhere in prose (`McpToolsetAssemblerTest`, `ProfileRouteManifestTest`, `RecordingSessionTest` on both sides) exist so that drift is loud — when one fails, update the prose too, don't loosen the test.

### Frontend
- Vitest (`npm run test` in `jeffrey-microscope/pages-microscope`). `profile-routes.json` is a snapshot of `profileChildRoutes.ts`; regenerate rather than hand-edit.
